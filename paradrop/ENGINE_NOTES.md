# Engine notes: Paradrop

Findings of 2026-10-25.

- `Data/craftrules.xml` keeps a `Paradrop` craft (abilities are "crafts"), disabled with `FROM None` and `PREQ0 disable`. The same is done for other cut abilities: Pilfer Resources, Assimilate, Rally!, Restock Supplies, Blow Tread, Research Project, Move Capital Here.
- `riseofnations.exe` has no "paradrop" string. Crafts are probably known to the code by their place in `craftrules.xml`, not by name, so the order of the crafts must not change.
- `FROM` / `FROM2` name a unit line by its first unit (`Catapult` for the siege line, `Machine Gun`). `FROM Airbase` was tried on 2026-10-25: the override was loaded (`ron_camera.log`), but the Airbase showed no button. Building buttons such as Raze (`FROM Small City`) seem to be fixed in the code.
- The caster needs craft points (`MANA` in `unitrules.xml`) of at least the ability's `MANA` (500 for Paradrop). Units with `MANA`: General 1000, Spy 1000, Supply Wagon 500, Scout 500, Explorer 1000, the Commando line 1000-2000, the Iroquois scouts, fighters 300-600, Bomber 600, Strategic Bomber 750.
- The Commando line is the likely intended caster: it is the only line that already has field abilities of this kind (Sabotage, Sniper).
- The Airbase has `GARRISON_MAX 0` in `buildingrules.xml`. If the drop takes garrisoned units, this has to change. The Data Center mod already overrides `buildingrules.xml`, so such a change has to be made on top of that file.
## The Airdrop ability (camera-smooth/src/airdrop.c), found 2026-10-25

Names from `sbl/rise_z.map`, looked up with `tools/rdis.py` (find / dis / xref).

- **A targeted ability, end to end.**
  - Unit panels add one button per castable craft with `Options::add(4, GRID_X, 1, craft type, disabled, 0)` (`UnitOut::make_options`, loop over 0x275..0x2AB). Option code 4 = "craft". `Options::add(code, column, row, type, disabled, 0)` 0x0072C290 is called on `*0x00C06204`. The Airbase's air commands are `add(0x2B/0x2C/0x2E, 0..2, 3, -1, 0, 0)` in `BuildOut::make_options` 0x00629ED0.
  - Clicking calls `Options::exec` 0x0072C4B0, then `Options::exec(Option *, int)` 0x007188C0, which copies the option to `Options+0x7C` (the pending option) and switches on its code.
  - A craft goes to `Options::do_spell(type, int)` 0x0071D7A0. It needs `GroupData::get_spellcaster(type)` 0x0070CA10 and `get_valid_spellcaster(type)` 0x0070C770 to answer >= 0 for the selected group. For an area craft it then starts the targeting (cursor 0xD for Paradrop).
  - The click on the map calls `Options::target_spell(type, int, int, Coord x, Coord y)` 0x0071DDA0, then `GroupOut::validate_spell` 0x007095E0 (0 = valid), then `CommandManager::issue_spell` 0x00941B80, which sends the group and the command.
  - On every machine, `CommandPackage::process_spell` 0x00948340 calls `Group::action_spell(type, int, int, x, y)` 0x006FE1A0. That validates again, gives cast orders, and `Unit::do_cast` 0x005EBFE0 (the Paradrop crash) carries them out.
- **Groups.** Member count `+0xC`, player `byte +0x4A`, member ids `short +0x8CC`. The local player's selection is `*0x00E8D444 + [console+0x2A0] * 0x9F0`. The local player is `[*0x00C06210 + 0x298]`.
- **Objects.**
  - `Objects *` is at `*0x00C0618C`. Per player, `+0x14 + 0x1C*p` points to the object pointers by id; unit ids are 0 .. `[+0x15C + 4p]` - 1, building ids 2000 .. `[+0x184 + 4p]` - 1. The same arrays sit at `0x00C0AB84 + 0x1C*p`; `0x00C0AEC0 + 0x1C*p` are the units.
  - An object's slot is in use when `byte +8` bit 0 is set.
  - Fields: owner `byte +9`, id `short +0xA`, x `+0x10` and y `+0x14` (both XOR `0x63637`), `TypeData *` at `+0x18` (type index at `+4`), damage taken `+0x24` (hits left = virtual `+0x11C`(0) - damage), the unit's model `**(+0xF4)`.
- **Making and moving units.**
  - `Objects::init_unit(player, type, x, y, -1, -1, -1)` 0x0065E0C0 (on `*0x00C0618C`) returns the new id and finds a free spot near (x, y) itself (`UnitType::find_nearby_spot`).
  - `Unit::go_to(x, y, 2, 0, 0x300)` 0x005F7A50 is a normal move order (through a temporary group).
  - `Unit::go_inside(building, player, 0)` 0x0061A2E0 is what `Build::train` uses to put a new aircraft in its Airbase.
  - `Object::disband(0)` 0x006455C0 is the Delete key for units.
- **Coordinates.** `Coord`: 192 per tile (`TCoord = div_3_table[Coord >> 6]`, table at `*0x00CAE5FC`). The map is `World[0] * 768` by `World[1] * 768` (`*0x00C06188`). The ground height is `TerrainOut::find_tcoord_z(&z, tx, ty, 0)` 0x008544A0 on `*0x00C06218`, in the same units as a model's z (`GuyData +0x14`, previous frame `+0x70`). A flying unit's model is at least 0x96 above the ground.
- **Time.** Game time is `[*0x00C061EC + 0x550]`, in 1/15 s (the timer divides by 15); `+0x854` is the fraction of the frame being drawn. `GameDaemon::process_all` 0x00732700 runs once per simulation frame (from `Game::do_frame`).
- **Resources.** The treasury is `[[leader + 0x6EB8] + 4*r] ^ 0x8221`, at the same scale as costs. Resource order: food, timber, wealth, knowledge, metal, oil.
- **Other.** Selection: `SelectGroup::add(id, player, int)` 0x00716C10. Diplomacy: `LeaderData::is_enemy(player)` 0x006EBAA0. Age: `LeaderData::has_tech(0x225)` 0x006E0C80 = Modern Age. Types: Airbase 0x1BF; cities 0x19E..0x1A0 (Small, Large, Major).
- **Frame order** (`Game::do_frame`): ... `Leaders::strategy_all`, `GameDaemon::process_all`, `Armies::process_all`, `Objects::process_all` 0x0065DCE0 (units move, air physics set the model's height), `Objects::inc_time`, `GraphicEvents::process`, ... A unit's model height written in a hook after `Objects::process_all` is what gets drawn, interpolated from the previous frame like any move.
- **Drawing does not use `GuyData::get_render_z`.** Its only caller is `GuyOut::graph_inc_frame`, so a hook there changes nothing on screen. That was the first try at the landing (2026-10-25: the drop worked, the helicopter did not come down).
- **Graphics families.** Every family in `unit_graphics.xml` is named by some unit's `GRAPH`; names compare without case (`ArmedCaravan` = `ARMEDCARAVAN`), so none is free. A unit that needs its own look takes over a campaign-only unit's family: the Paratroopers use `FOUCHE` (Advisor Fouché), with Assault Infantry's entry in a black texture and Assault Infantry's sounds.
- **Finished buildings.** `ObjectData::is_active_build()` 0x0046FB40 checks three things: the slot is in use, the object is a building (virtual +0x20), and it is active, i.e. not a construction site (virtual +0x4C). `BuildOut::make_options` also runs for a building under construction, so the Airdrop button needs this check (it showed on an Airbase still being built, 2026-10-25).
- **Craft prices.** A craft's `COST2` (in tens, as `40f/35o`) is what the tooltip shows with resource icons. Casting through the game would charge it; Airdrop never reaches the game's casting, so the mod charges it itself.
- **The two caster questions (found 2026-10-26).** `Options::do_spell` 0x0071D7A0 first asks `GroupData::get_spellcaster` (-1: return silently), then `get_valid_spellcaster` (-1: red feedback with `MessageWin::add_feedback` and `SoundGlobal::play(0x40)`; otherwise the targeting starts). `Options::describe` asks only `get_spellcaster` and writes the price line only when it gets a caster. airdrop.c answered both with the ready Airbase, so the price vanished while the Airbase was cooling down or the player could not pay; now `get_spellcaster` gets any owned Airbase of the group (`any_base`), `get_valid_spellcaster` the ready one.
- **Population (found 2026-10-26).** A player's population now is `int [leader + 0x940]`, the limit `int [leader + 0x7E4]` (both plain, not encrypted; `IFaceMainBase::draw_pop_cap` prints them). `LeaderData::check_population(TypeIndex)` 0x006E1330 (`ret 4`) returns 1 when `pop + POP(type) > limit`; `POP(type)` = `[[0x00C0A274][type] + 0x2F0]`. The game's production calls it (`Build::do_queue`, `Build::process`, `Build::activate`); `Objects::init_unit` does not, so a unit made through it can go past the limit. The counter itself moves in `Unit::set_type` (adds the new type's POP when it is not 0, takes the old one's off); `Unit::close` also addresses it, presumably to give it back; `init_unit` takes it off again for every soldier of a squad but its leader, so a squad counts once. The drop therefore takes population (helicopter 1 + 2 squads x 1), and `airdrop.c` now refuses a drop without room for all of it (`has_room`, in `ready_base` and `launch`).
- **Aiming state (found 2026-10-26).** `Options::exec` copies the clicked option (16 bytes: code, type, count, disabled) to `Options+0x7C` (`movups` at 0x007190BC), so `+0x7C` = code (4 = craft) and `+0x80` = type. `Options::do_spell` starts an area craft's targeting with `[Options+0x24] = 1` and `Cursors::set(0xD)` (Paradrop) and writes the instructions line. `Options::reset` 0x0072C040 clears `+0x24`, `+0x74`, `+0x20`, sets `+0xB0` and `+0xE4` to -1 and the cursor to -1, but leaves `+0x7C` / `+0x80`.
- **The click.** `Options::picked_spot` 0x00721C40, for a pending craft with area flag 8 at `[spelltype + 0x1C8]`, takes the type from `+0x80`, calls `Options::reset`, then `target_spell(type, -1, -1, x, y)`. `Options::target_spell` 0x0071DDA0 (`ret 0x14`) calls `reset` again, then, unless `game+0x820 & 0x10` (replay), `GroupOut::validate_spell` and `CommandManager::issue_spell`. So the targeting always ends with the click; airdrop.c re-arms it on the next frame with `Options::do_spell(0x284, 0)` 0x0071D7A0 (`ret 8`; a second argument other than 0 casts at once at the console's mouse position `[console+0x2D4/0x2D8]`).
- **What follows the cursor.** `Scene::render` calls `Options::draw_cursor_follows` 0x00723C00 every frame (after setting the GraphSys sort depth `+0x164` to `[0x00C8C32C]`). `Options+0xB4 / +0xB8 / +0xBC` are the world point under the cursor (x, y, z in Coord); `+0xB0` is the building type being placed (-1 none). For a city it draws the territory radius with `draw_circle`.
- **`draw_circle`** 0x008C6040: `void draw_circle(Coord x, Coord y, Coord z, int radius, Color, CircleType, int, int, int, float)` compiled with radius in ecx and CircleType in edx; the stack holds x, y, z, the 12-byte Color, then -1 (line width default `[0x00EB0FAC]`), 1, an unused int and the float 0.0; cdecl (`add esp, 0x28`). With type 0 and a radius under 0xC0 it draws through `GraphicPieces::draw_circle`, otherwise `CircleRender::draw_general_circle`. Colours: `TeamColor::get_unit(Color *out)` 0x008C2DB0 (`ret 4`) on `team_colors` 0x00E39CE0 + 0x64 * `byte [leader + 0x6928]`; the game then replaces the alpha byte only (`& 0xFFFFFF | 0xCF000000`). `Color::set(r, g, b, a)` 0x0042D820 writes `0xAABBGGRR`, two 16-bit forms at +4 / +6 and 2 at +8.
- The mod's icon takes the Paradrop craft's own cell (4, 4) of `art/iface_unit_orders.tga` (TEX_ORDERS_0), which nothing else uses.

## Helicopter rotors

- The game's helicopter models (`chopper.bh3`, `hind.bh3`, `attackchopper.bh3`) have no rotor blades in the mesh.
- The rotor is drawn separately: `unit_graphics.xml` gives the unit `<EXISTEVENT starttime="0" endtime="9999" anim="CHAR_DEFAULT" type="CopterBlade" node="2"/>` for every animation (CHAR_DEFAULT, CHAR_WALK, CHAR_ATTACK2, CHAR_JOG). `CopterBlade` is an "ammo" in `effects_graphics.xml`: model `helicopter_blade.bh3` (8 vertices, two crossed quads 61 x 157 units, flat), texture `helicopter_blade.tga`, render state "Smoke Blend". `ChopperBlade` (`mainrotor.bh3`) and `ChopperRotor` (`tailrotor.bh3`) are two more of the same kind.
- `node="2"` is a skeleton node of the model. The animation `Helicopter Propspin` (`art/helicopter_propspin.bha`) is set for CHAR_DEFAULT and CHAR_WALK and probably turns that node.
- A new transport helicopter therefore needs a mesh plus a node at each rotor hub, and one `EXISTEVENT CopterBlade` per hub.

## BH3 and BHA, as far as needed for a unit (checked on chopper.bh3, 2026-10-25)

- Chunks `[u32 size incl. header][u16 type][u16 children]`. Containers: 0 (file root), 1 (mesh), 6 (node), 8 (animation track); everything else is data. The child count includes a node's own type 7 chunk. `tools/build_bh3.py` parses and writes them back byte for byte (checked on chopper.bh3, hind.bh3, helicopter_blade.bh3, helicopter_propspin.bha).
- Mesh: 2 = `u32 n` + n x float4 (w = 1); 3 = `u32 n` + n x float3 normals, then n x 4 bytes of `0xCD` (uninitialised memory, the chunk is sized as float4); 4 = `u32 n` + n x float2 UV, V from the top; 5 = `u32 index count` + u16 indices. 91 % of chopper.bh3's triangles wind against their normals (`cross(b - a, c - a)` points inward).
- Axes: X length (nose at -X), Y up, Z width, the same as Tripo's exports. chopper.bh3 runs from -28.6 to 86.8 in X and from -5.7 to 28.9 in Y; the main rotor sits at X = 0.
- Node data (type 7): `[u32 first vertex][u32 vertex count][u32 name length][name\0][quaternion x y z w][position x y z][the quaternion's x again]`. `center` owns vertices 0..n (the whole mesh); the other nodes have first vertex = n, count 0; the root has 0, 0.
- chopper.bh3's tree: root `smoke node 3` (quaternion (-0.5, -0.5, -0.5, 0.5), an axis swap) -> `center` (position (0.39, -28.2, 0)) -> `ammo node 0`, `ammo node 1` (rocket pods), `ammo node 2` (main rotor, quaternion 90 degrees about X) -> `dummy`, `ammo node 3` (tail rotor) -> `dummy`, `smoke node 0`, `smoke node 1`. The children's positions are plain mesh coordinates: `ammo node 2` (0, 28.0, 0) is the mast top, `ammo node 3` (77.5, 15.9, 0) the tail.
- `node="N"` in `unit_graphics.xml` events is the N of "ammo node N": RELEASEEVENT rockets on nodes 0 and 1, CopterBlade on 2, the tail propeller (`B-25Prop0`) on 3.
- helicopter_propspin.bha follows the same tree: one type 8 track per node, each starting with a type 7 key list `[u32 key count][u32 ?]` then 9 floats per key (quaternion, position, one more, time; the last key has 8). The root track bobs (small positions); `ammo node 2`'s track spins about Z in 12 keys; `ammo node 3`'s spins the tail propeller in 25 keys. Track positions are offsets, so a model may move its nodes.
- First try in game (2026-10-25): with one animation added to `anim_graphics.xml` ("Chinook Propspin", 2074 instead of 2073) and the four helicopter entries pointing at it, the game stops while building a new game with "NO DEFAULT UNIT GPIECE - VERY BAD" (raised at `0x0090C609`, a search through the unit graphics pieces). Suspected cause: the added animation (the game also refuses extra buildings). Now the spin reuses "LightBomber Default", which nothing names (no data file, scenario or the exe; names compare without case), so the count stays 2073. Result: the same error. The (fixed) log shows the game reads `anim_graphics.xml` and stops with the error before it opens `chinook.bh3` or the `.bha`, and the edited entries differ from the originals only where intended.
- Next suspect: the game lists folders with `_wfindfirst64i32` (CRT, called at `0x00A2CE83` and `0x00A2E147`), which goes through `FindFirstFileExW`; the file overrides do not hook that, so a file that exists only in `mod_override\` may look missing. Test: the three chinook files copied into the game's own `art\` folder as well (new files, nothing replaced). Result: the game starts and the helicopters show as the Chinook. Confirmed: a model must be visible to that search. Fix in `camera-smooth/src/override.c`: `FindFirstFileExW` is hooked too, and a search for one exact file goes to `mod_override\` when the file is there. Wildcard searches are logged ("folder search ... (not merged)") but not merged yet. The copies in `art\` were removed again; to confirm in game that the hook alone is enough.
- Unit textures: 256 x 256 RGBA TGA. Player colour = grey pixels with alpha about 66 (chopper.tga: 3149 pixels, RGB 90); the rest alpha 255.

## Test of 2026-10-25: the button shows, casting crashes

With `FROM Commando` / `FROM2 Bomber` the button shows. Casting it crashes the game: access violation at `riseofnations.exe+1EC14E` (static VA `0x5EC14E`, base `0x400000`). The dump is in `%LOCALAPPDATA%\CrashDumps\riseofnations.exe.20352.dmp`.

- Crafts are object types `0x275 + index in craftrules.xml` (55 crafts: `0x275`..`0x2AB`). Paradrop is index 15, type **`0x284`**. The code tests the craft range with `cmp eax, 0x275 / cmp eax, 0x2ac`.
- `0x5EBFE0` (thiscall, `ecx` = casting unit, one stack argument = order, `ret 4`) carries out a craft on a **target object**. `order->vfunc[0x7C]()` returns the order data:
  - `+0x08`: target object index;
  - `+0x0C`: target owner (player) index;
  - `+0x1C`: "started" flag;
  - `+0x20`: craft type.
- The target object is looked up as `[[0xC0618C] + owner*0x1C + 0x14][index*4]`. For an area craft both fields are -1, the list pointer is null and the read at `-4` crashes. Paradrop is the only craft with the area flag `d`, so this path was never finished for area targets.
- Paradrop has its own code in three places:
  - `0x709B72`: command issue. It goes through the selection (`[ebx+0xC]` count, entries at `ebx+0x8CC`, objects in `[0xC0AB84 + player*0x1C]`) and gives each selected unit the order.
  - `0x71DB39`: the craft -> cursor table (Paradrop -> cursor `0xD`, the `SC_paradrop` cursors).
  - `0x8C720A`: an interface check on the current cursor craft.
- Conclusion: targeting and the order exist, but carrying out the drop does not. A working Paradrop needs its own code in the DLL: catch craft `0x284` at the start of `0x5EBFE0` before the object lookup, and do the drop there.
