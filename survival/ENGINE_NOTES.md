# Survival: engine notes

What the survival script relies on, found 2026-10-29 in the game's own scripts (369 `.bhs` files under `scenario\` and `conquest\`) and the `ScenarioFuncSet::` symbols (879, in `tools/rdis_syms.txt`).

## Game scripts in the setup screen

- Every folder under `scenario\Scripts\` with a `.bhs` in it is a choice under **Script** in the custom game setup (the game ships `Auto_Pause` and `No_Nukes`; our `Art_Test` works the same way). The folder name is the name shown.
- The game style list (Survival of the Fittest = `GAMESTYLE1` in `Data/help.xml`, the vote button in `interface.xml`) is fixed in the exe; a new style would need the DLL.

## The script language

- C-like. A `scenario { ... }` block; its plain code runs on every script pass, `run_once { }` once, `trigger name (condition) { }` once until `enable_trigger("name")`. `static` variables keep their value between passes; arrays: `static String a[] = ["x", "y"];`, `a[i]`, `a.length`. Strings join with `+` (also with ints). `rand_int(lo, hi)` inclusive. Library files are `include`d (`scenario\scriptlibrary\`).
- Timers: `set_timer("name", seconds)`, `timer_expired("name")`, `stop_timer("name")`.
- Ages: `age(p)` / `get_current_age(p)`, 0 = Ancient .. 7 = Information (`airliftsetup.bhs`: `if (age(1) == 0)`). `gain_next_age(p)`, `lose_current_age(p)`.
- Players: `num_players()`, `num_human_players()`, `is_human(p)`, `is_defeated(p)`, `have_war(a, b)`, `get_leader_difficulty(p)` (the setup difficulty; numbering to be confirmed), `get_difficulty()` (campaigns, 1..5).
- Units: `create_unit_in_group(p, x, y, "type", n)` adds n units to p's default group; `clear_group(p)` empties it; `group_attack_to_order(p, x, y)` attack-moves the group. `create_unit_upgrade` makes the player's current upgrade of a line instead (no use for a player without upgrades). Type names compare without case.
- Iterating: `find_all_military(p)`, `find_idle_military(p)`, `find_all_unit(p, "")` return the next unit on each call; the campaigns loop `num_military_units(p)` times. `find_unit(p, "")` = any unit.
- Cities: `find_capital(p)` returns the capital's **name** (String); `find_city_id(name)` its object id; `object_position_x / _y(p, id)`.
- Map: `get_map_size()` (square), `map_is_land`, `map_is_passable`, `territory_owner(x, y)`, `is_on_screen(x, y)` (the local camera: differs between machines, so only in single player).
- Keeping a player without cities alive: `disable_city_defeat(p)` (the Alexander campaign does it for the attacker). AI parts off: `disable_production_ai`, `disable_city_ai`, `disable_combat_ai`; `disable_take_attrition(p)`.
- Messages: `print_game_msg(text)` (chat area), `show_notice(text, "city_under_attack_notice", 1)` (the announcement with an icon; other icons: `launch_notice`, `capital_notice`, `reinforcement_notice`, `defeat_notice`, ...).
- End: `victory(p)`, `defeat(p)`.

## Compiling (learned the hard way, 2026-10-29)

- A script that does not compile only gives "did not compile successfully or could not be found" in the setup screen. The compiler's messages go to `OutputDebugStringW` (`Compiler::comp_error` 0x009BED80), e.g. `ERROR: survival.bhs (Line 82): Can't convert "bool" to "single". Explicit cast required`. Any DBWIN listener (DebugView, or a few lines of Python on the `DBWIN_BUFFER` / `DBWIN_BUFFER_READY` / `DBWIN_DATA_READY` objects) shows them; the game's own logs do not.
- Line numbers count CRLF line ends only: with LF-only files every error is "Line 1". Keep `.bhs` files CRLF.
- Typing is strict: a comparison or `&&` gives `bool`, which does not go into an `int` (`ok = a && b;` fails). Use `if (...) ok = 1;`. Function results typed `48` in `Data/scriptfunctions.xml` (`timer_expired`, `map_is_land`, `object_position_x`, ...) go into ints and into conditions fine. `float` variables with `(float)` / `(int)` casts work; `sin` / `cos` take degrees.
- `Data/scriptfunctions.xml` lists only the editor's functions (no `set_timer`, `print_game_msg`, `rand_int`...); the compiler knows all 879 `ScenarioFuncSet` ones.
- `time()` is the game time in **minutes** (`[game + 0x560] / 60`); timers are in seconds: `set_timer` stores `[game + 0x560] + seconds` with `ScriptTimers::add_timer(String &, int)` 0x00A049E0, at most 100 timers.
- `is_seen(who, whose, object)` is about an object, not a tile; there is no tile-visibility function. "Out of sight" is approximated with `any_object_near(defender, 1, x, y, 16)` being false.
- `add_flag(x, y)` adds a scenario marker (`ScenarioData::add_component`); it does nothing in multiplayer (`game + 0x820 & 4`).

## The DLL side (camera-smooth/src/survival.c)

- The script tells the DLL what it needs through timer names, caught in `ScriptTimers::add_timer`: `surv_end`, `surv_wave`, `surv_boss` (the clocks), `surv_plan <length> <first wave> <boss every> <boss delay> <spacing>` (the wave bar; a boss comes `<boss delay>` seconds after every `<boss every>`-th wave; the intervals are times `<spacing>`; the last three may be missing in older scripts: 5, 30 and 1), `surv_ring <band> <map size>` (the no-build band along the edges, tiles) and, from version 2, `surv_zone x0 y0 x1 y1`. Saved games restore the timers without `add_timer`, so the script sets `surv_end`, the plan and the band again every minute.
- The clocks are drawn after `IFaceMainBase::draw_timers` 0x0080B060 (every frame from `setup_progress_buttons`; it draws the game's own clock lines right-aligned at screen width - 10, y 45, with font "timer_size", int string 0x1511C) through `Buffer::write_right_l(String const &, x right, y, len)` 0x0050F9C0 on `Window::screen` 0x00ED8010. The screen Buffer's text colour is at 0x00ED80A0 and its shadow at 0x00ED80DC (12-byte Colors), current font at 0x00ED808C.
- The zone: `BuildTypeData::blocked_site(x, y, player, int, int *)` 0x00636A50 returns 0x18 inside it. Every caller (placement cursor, `Group::action_build` on every machine, the computer players, walls) respects it. Its codes and their messages (`BuildTypeOut::say_blocked` 0x00635C50, text from `translated_strings.xml`): 0x01 existing building, 0x08 invalid location, 0x12 must be adjacent to friendly territory, 0x17 cities in friendly territory, **0x18 "Can't build in enemy territory."**, 0x1A within your own territory, 0x22 map boundaries, 0x24 explored territory, 0x2D no new city for 5 seconds. The rest: `say_blocked`'s jump table at 0x006360D4 (index code - 1), each case adding a `translated_strings.xml` offset (entry = offset / 0x14) to `*0x00C8CD00`.

## The menu button (found 2026-11-10)

- The main menu's buttons are `Data\topmenu.xml` `BUTTON`s; a click ends in `TopMenu::check_result(String const &name)` 0x0059B1E0 (from `main_menu` 0x0059BF70, `sub_menu` 0x0059C030 and `TopMenuSelection::on_button_clicked` 0x0059E930), which compares the name with internal strings (`int_str_array + 0x10 + offset`): "quit" 0x57E4, "back" 0x21C0, "solo" 0x1DC54 (Quick Battle: returns GameIndex 1, the caller opens the solo `SetupWin`), "ctw" 0x73C8, "solo_menu" 0x21764 (opens the "SOLO" sub-menu, 0x1A1D0), "mp_menu" 0x2178C, "options" 0x23A0, "options_menu" 0x217A0, "scenario" 0x8264, "tutorial" 0x16FD0. An unknown name falls through. survival.c swaps the "survival" argument for the "solo" String and remembers the click.
- The menu's frame follows its buttons: the main menu's seven buttons get a frame one button taller than the Solo menu's six, in the same 768-high window.
- The menu titles are translated by the game through `translated_strings.xml` (`STRING hash=...`, the English text's hash), not through per-language copies of topmenu.xml; a new title needs an entry there to be translated.

## The game's script and the setup (found 2026-11-10)

- `Game+0x500` (String) = the script's file name without `.bhs`, `Game+0x528` (String) = its folder; `GameInfo::get_full_script_path` 0x005D4C80 joins them (adding `\` and `.bhs`). Set by `SetupWin::set_script_path` 0x005B7AA0 from the base folder (`SetupWin+0x1E80`, the prefs' scripts folder with the content folder in front = a full path; `+0x1E94` the custom scripts folder of the profile) plus the choice's text at `ConnectionData+0x2C6`.
- `SetupWin::setup_game` 0x005B3860 sets `ScenarioData::load_scenario_script` 0x00CC21B0 = 0x80 when the Script combo (`SetupWin+0x21EC`, selected index `+0x568`) is past "none", and calls set_script_path. `Setup::build_game` compiles the script (0x005AD826) only when `load_scenario_script` is set, after the map, the empires and the herds are made. `load_scenario_script` is saved with the game (`ScenarioData::walk_data`).
- So at map time (`Map::make`, earlier in build_game) the script's name is already known: a Survival game is `load_scenario_script != 0` and `Game+0x500` == "survival", not in a Conquer the World battle (`Game+0x822 & 2`).

## Random maps (found 2026-11-10)

- `Setup::build_game` makes the map with `Map::new_map(style)` 0x006A0950 (a class per map style: `MapOldWorld`, `MapGreatSahara`, ..., and `MapGrass`), then its virtual `make` (`Map::make` 0x0068BC90). The style index is `Map+0x10`; `Map::map_file_mapping` (ObjectArray<String> at 0x00C89938, data `[0x00C89948]`, 0x14 bytes each, filled by `Map::init_map_file_names` 0x006A10C0) names its XML: 6 OLDWORLD, 7 SAHARA, 8 AMAZON, 9 HIMALAYAS, 10 SOUTHWESTMESA, 11 AFRICA, 12 MEDITERRANEAN, 13 OUTBACK, 14 GREATLAKES, 15 WARRINGSTATES, 16 NEWWORLD, 17 COLONIALPOWERS, 18 EASTINDIES, 19 EASTWEST, 20 SEAPOWER, 21 NILEDELTA, 22 BRITISHISLES, 23 DEFAULT (the editor's, skipped by make), 24 CONQUESTMAP, 25 CONQUESTMAPSEA.
- `Map::make` writes `"mapstyles\" + name` to `Map+0x114`, then `Map::load_map_data(int, int)` 0x0069DAD0 reads `.\mapstyles\default.xml` and then `Map+0x114` (truncated at its last '.', plus ".xml"). Changing `Map+0x114` at the entry of load_map_data loads another file: survival.c's `mapstyles\SURVIVAL`.
- Then `make` calls the virtual `make_continents(int players)` (vtable +0x40) at 0x0068BDFB: `mov eax,[ebx]` / `mov ecx,ebx` / `push edi` / `call [eax+0x40]`, 8 bytes from 0x0068BDF6. After it: diagonal land fix, coastlines, regions, `TerrainGroups::place_all` (the GROUPENTRYs), forests, resources, rivers. The only per-class code is make_continents (and MapConquest's).
- The World (`*0x00C06188`): `+0` / `+4` width / height in tiles, `+0x134` the cells (0x1C bytes each, row-major), cell `+2` the land kind: **0 land**, 2 water, 1 another water kind (`Map::invert_land` 0x0069D880 turns 1 and 2 into 0 and everything else into 2). `World::wipe` 0x006B2C00 empties the starts (`+0x84` and `+0xA0` counts). Starting locations: `World::add_starting_location(x, y)` 0x006B2DE0 (tiles), x in the SimpleArray at `+0x80` (count `+0x84`, data `+0x90`), y at `+0x9C` (data `+0xAC`).
- `MapGrass::make_continents` 0x00695050 (no map style uses it): wipe, every cell's `+2` = 0 (all land), the starts on a circle of radius width/2 - width/8 round the middle, then `Regions::find_all`. It does not use `this`, so any Map can call it. survival.c calls it, then moves start 0 to the middle.
- Each player's start: `Setup::build_empire(player, start)` 0x005ABB80 (player = the Leaders index, `Leaders` 0x00E3A390 + player * 0x6EEC, flags `& 1` in the game, `& 4` human), from build_game's loop over the players; it builds the cities and units at that start. survival.c gives the first human start 0 and the others starts 1, 2, ...
- `mapstyles\*.xml`: `SEA_MAP` (0 land map), `TILESET` / `TILECHANCE` (types seen: dirty, dirty_2, snowy, arctic, sw_desert, gs_desert, jungle, african_savannah, m_steppe, m_steppe_2, m_steppe_3, autumn, early_autumn, late_autumn, tropical, tropical_wet), `TERRAIN_GROUPS` (`GROUPENTRY` mountains / trees / rocks / cliffs / oil, pattern player / world / continent / corner, sizes and distances, "SCALE" scales with the map's side), `BONUSES`, `FISH`, `GOODIES`, `RIVERLIST` (empty = no rivers). A section left out comes from default.xml (default.xml has rivers, mountains and cliffs).

## Drawing the wave bar

- In draw_timers' frame (the same place as the clocks) the bar is drawn with `IFaceRenderManager::add` 0x0051F3D0 on `iface_render_manager` 0x00EBD1C0: an IFACETEX of the IFACEMAINBASE block (found through qol.c's `qol_iface_tex`, `surv_disc` / `surv_ring` / `surv_glow` / `surv_pip` from `art\revived\survival_bar.tga`, the boss skull `kills_skull`), tinted by the colour (0xAABBGGRR), or a plain rectangle (type 5, no texture). Rect = left, right, top, bottom in the window's units; `GraphSys+0x164` is the depth (higher = in front), stepped per layer so the glows, discs, rims and skulls stack in order.

## The hero (2026-11-10)

- `ScenarioFuncSet::create_unit(p, x, y, type, n)` returns `add_unit`'s `[esp+0xC]`, the id `Objects::init_unit` gave the (last) unit made, so the script can keep it. Script player p is the game's player index p - 1 (`kill_unit`, `object_position_x`: `dec`), so the DLL gets `P - 1`.
- No script function reads a timer back, and none tests a unit alive (`object_position_x(p, id)` gives -1 for a dead or invalid one), so the DLL keeps the hero's squad itself (ranks.c, every second from the soldiers it knows).
- Upgrading one unit as research does (`Leader::gain_tech` 0x006DDBCB): `unit->vtable[0x84](new type, 0)` for each soldier. The type by name: `ScenarioFuncSet::get_type_index` 0x00A03480 takes the String in ecx and 0 in edx; the nation's own version: `LeaderData::get_graft(int)` 0x0047DF40 on `Leaders + p * 0x6EEC` (what add_unit does).
- A squad is refilled up to its type's `UBER_SIZE` (+0x308) when healed; readers of +0x308 include `Unit::repair_damage`, `Unit::come_out`, `Object::take_damage`, `Leader::gain_tech` (a new type with a larger UBER_SIZE takes the old squad's state, 0x006DDAD5..).
- "Other Nations" did not hold at 1 either (2026-11-10: the log showed 8 players again, and the script's removal of the 6 extra computer players showed "Emperor ... defeated." each): its combo is hidden, so the draw-time lock never ran, and the screen refilled it from `Game+0x27`. It is now in the fixed rules (combo, Game byte, `make_combo_change` before setup_game). The script also keeps any extra computer enemy in the game, emptied, with `disable_city_defeat` (no defeat notice), and counts only you and your allies as defenders (`p == H || !have_war(H, p)`).
- Special resources in one corner (2026-11-10, seen on the minimap): the map style lays its "player" woods, rocks and resources round every start, the battle director's too (on MapGrass's ring), though the script removes its city at once. Now every start is in the middle while the map is made (Map::make and `place_resources(players)` read one start a player, so the count stays), and the battle director gets a start of its own at the top edge from `World::add_starting_location` 0x006B2DE0 in the build_empire hook, after the map. SURVIVAL.xml's world resources had distances with SCALE that left almost no room on a Big Huge map; plain distances now.
- The hero's light (2026-11-10): `UnitOut::draw_overlays` draws the "CTWGlow" effect (effects_graphics.xml AMMO "CTWGlow", `CTW_gen_effect.bh3` with the `CTWGeneralGlow` animation; its index is `GraphicPieces+0x1048`, set in `GraphicPieces::init`) over a government hero (`UnitData::is_gov_hero` vtable +0xC8, inlined as type FLAGS `+0x2B4 & 0x4000000`: the Patriots). ranks.c's glow hook makes its three "no light" exits (0x006159A9, 0x006159E3, 0x00615A20 -> 0x00615B5C; light = 0x00615A28) ask whether the unit (esi = player, edi = id) is the Survival hero.
- No mountains meant no Metal (mines stand on mountains): SURVIVAL.xml has a home mountain (pattern player, size 2, 6-9 tiles from the city) and small world mountains away from the edges.
- Two heroes (2026-11-10): ranks.c keeps up to 4 hero slots (`g_heroes`); the script names the slot: `surv_hero P id slot` and `surv_heroage P slot name` (slot 0 the infantry squad, `li[]`; slot 1 the rider, `riders[]`, the Stable's GRID_X 0 line: Light Horse .. Hussar, then Armored Car .. Armored Cavalry, which cost Oil and Food, no Metal). Cavalry has UBER_SIZE 1: the rider is one unit.
- The hero choice (2026-11-10): no script function reads anything the DLL sets, but `ScriptTimers::check` 0x00A04B80 (timer_expired) gives 1 for an expired timer (and removes it), 0 for a running one, -1 for none. The script sets "surv_herochoice" 99999 s ahead; survival.c's add_timer hook hands back another end second (the stub writes the C function's result into the call's argument), the present second for the rider, so `timer_expired("surv_herochoice") == 1` means cavalry. The choice is the Survival setup's button (unitbans.c's Units button, drawn and clicked differently there) and `[survival] hero` in ron_camera.ini.
- Squad refill: `Unit::repair_damage` 0x0060DE10 brings a soldier back (Objects::find_free, the captain's type, linked into the chain `+0x8E` / `+0x90`, damage = hits / UBER_SIZE, flags `+0x68` copied, not `+0x6C`) while `UnitData::curr_uber_size(0)` < `[type+0x308]`, read at 0x0060E027 (`mov esi, [eax+0x308]`, eax = type, edi = unit). ranks.c answers that read for the infantry hero with 3 + one per level 15 / 20 / 25 / 30; its new soldiers get the squad's experience at the next refresh (the `+0x6C` bits are not copied).
- Hero balance and marks (2026-11-10): ranks.c `hero_power` (100 / 133 / 200 / 233 / 300 % at 15 / 20 / 25 / 30) sizes the infantry squad (refill read) and, for the rider (one unit: the refill code wants a soldier chain, `[unit+0x90]` < 0 raises an Error::report), multiplies its hit points (`c_rk_unit_hits`) and its damage and attack rate by the square root each (`ranks_damage`, `ranks_recharge`); experience gains are divided by it. The Patriots' light is off (glow_install not called); `ranks_draw_hero_marks` draws the medallion over each hero's captain from rankfx.c's map window redraw.
- The setup's hero buttons: setupwin.xml PLAYERSWINSOLO BUTTONs "hero_inf" / "hero_cav" (hidden), shown by survival.c in the Survival setup: the players panel is embedded at `SetupWin+0x25D4`, its buttons found with virtual +0x424 (String const &, 0); drawn from unitbans.c's on_button_redraw hook; clicks through `SetupWin::on_button_clicked(String const &)` 0x005C5B50, vtable slot 0x00B3ADF0. The medallions are IFACETEX in setupwin.xml's SETUPWIN block too (find_tex looks there).
- Crash 2026-11-10 (opening the Survival setup): `find_button` (players panel vtable +0x424) was called with three arguments; it takes two (String const &, int) and, thiscall, pops only those, so the stack was 4 bytes off and survival_setup_checks read 0xFFFFFFFF. find_tex (+0xA4) takes three (String const &, int, int *).
- Script coordinates are tiles (TCoord; rules.xml: a farm is 4 tiles, 1 WCoord): `get_map_size()` gives 400 on Big Huge, where MapGrass's grid (Map::make) is 100x100 WCoords. `create_building(p, x, y, name)` 0x009F4D30: x, y to world units as tile * 192 + 96, refused (-1) for a non-building type, a player not in the game (leader flags &1 and &2), a point off the map, or a site `BuildTypeData::blocked_site` refuses (it accepts the codes 0, 0x1F and 0x20; survival.c's band answers 0x18, so nothing can be created in the band); otherwise `Objects::init_build` and the new building's id. `building_destroyed(p, id)` 0x009F1D80: 0 while it stands, 1 once it has died, -1 when there is no such object.
- Unit speed: unitrules.xml MOVES is 192ths of a tile a frame (15 frames a second): Slingers 28, about 2.2 tiles a second, so about 90 seconds from the edge of a Big Huge map to the middle.
- Teams: Game's player slots start at `Game+0x74`, 0x8C bytes each, eight of them: +0 a flags word (& 1 in use), +3 the leader's index (`[leader+8]`), +4 the team (0..3; 4 and up none, 5 an observer). `Game::init_teams` 0x0058AE70 counts them into `Game+0x5E0` (int[4], players per team); with Teams & Allies Barbarians at the Gates (`Game+0x24` = 3) it sets the team itself: 0 for the console's player, 1 for the others. survival.c's build_empire hook reads the team so the first human's allies start round the middle.
- `ScenarioFuncSet::make_alliance(p, q)` 0x009FBF90: `Leader::set_diplo(q, 2)` on p only (and clears two diplomacy cells both ways); survival.bhs calls it both ways.
- setupwin.xml: `top_inverse="N"` places a child N pixels above its parent's bottom (the game's own scenario editor's Delete button); the hero buttons use it to sit at the bottom of the solo players panel whatever its height.
- `ScriptTimers::check` really removes an expired timer (LinkListBase::remove_current before `return 1`): read a timer once a pass. An int in a script condition counts as true only above 0, so `!timer_expired(t)` is true for a running timer (0) and again for a removed one (-1): the start's clearing block ran all game, killing every wave unit on creation and the camps (fixed 2026-11-10 with a `cleared` flag). The wave block's second `timer_expired("surv_boss")` always saw -1.
- `Setup::build_empire` does not run in player order: the computer player 1 was built before the human player 0 (ron_camera.log). survival.c finds the first human by index.
- Player colours (`TeamColors::init` 0x008C3100, `team_colors` 0x00E39CE0, 0x64 bytes an entry): 0 red, 1 blue, 2 pink, 3 green, 4 yellow, 5 cyan, 6 white, 7 orange (the setup's colour combos 0x10 + row, item = this index). alternatecolors.xml (the colour-blind set) has grey in place of green; the normal set has no grey.
- `Objects::init_unit` 0x0065E0C0 reads the squad size from the type (`[type+0x308]`, UBER_SIZE) at 0x0065E0FF when it makes a unit, so changing it on the type for one `create_unit` (and back) makes one squad of another size; cavalry types have UBER_SIZE 1 (single units, no soldier chain). `ScenarioFuncSet::add_unit` 0x009E2220 creates the player's own version (`LeaderData::get_graft`). The game's types: `[0x00E85DDC][index]`.
- Squads bigger than 3 stack: a squad made with 6 soldiers (UBER_SIZE raised for its creation) drew 4 figures, the extra soldiers on top of the first ones. The game has only squads of 1 and 3 (unitrules.xml) and tests for them in several places: `Guy::set_anim` syncs a squad's animation only when `[type+0x308] == 3` (0x005DA817), `Form::categorize` 0x0072E250 sorts by `== 1`. Where a soldier's place in the squad is worked out was not found yet (not in `UnitData::uber_size`, which nothing calls directly).
- Squad chain: a soldier's `+0x8E` is the soldier before it (the captain for the first one only; a captain has bit 15 set), `+0x90` the next; `UnitData::get_captain` 0x00610AB0 walks up. Where soldiers stop: `Group::action_move_near` gives each soldier a spot beside its captain's destination (`UnitType::find_nearby_spot` at the type's size `+0x224`), +90 degrees for the one whose `+0x8E` is the captain, -90 for every other (0x00705CC0, the only such code): a triangle for 3, but a bigger squad piles up on the right. ranks.c's `hk_squad_angle` spreads a squad of more than 3 round the captain, one angle each (squads of 3 and less unchanged).
- Fixed with it: ranks.c's `captain_of` took `+0x8E` for the captain, so a squad's third soldier gave the second one as its captain.
- The player's moves go through formations: `Form::compute_dests` 0x0072CBA0 places a squad's soldiers beside the captain's place, the type's size (+0x224) to the side, the first soldier after the captain on one side (flag `[ebp-0x3C]` = 1 left from the captain, 0x0072CCAA; cleared at 0x0072D630) and every other one on the other side (0x0072D375 .. 0x0072D38F). ranks.c's `hk_form_side` (at 0x0072D385) puts them out further each: +1, -1, +2, -2, +3 sizes, a row (a squad of 3 as before).
- A squad bigger than its type's: `Unit::update_hits` counts the squad's maximum for the type's UBER_SIZE, so six soldiers showed 170 / 85. ranks.c's `c_rk_unit_hits` multiplies a hero squad's maximum (infantry or riders, 114 / 77 for two riders) by its size / the type's (`c_hero_uber`).
- Wonders from the script: `get_wonder_points(p)` (above 0 once a Wonder stands); `defeat(p)` and `victory(p)` end the game for a player. The setup's goal buttons reuse the hero buttons' machinery (on_button_redraw / on_button_clicked); setupwin.xml can load the game's own `art\iface_alerts.tga` under an id of its own (`TEX_REVIVED_ALERTS`).
- The package folder is named by the date (`dist\RON_Revived-<yyyy.mm.dd>`): after midnight a new one is made and the old one stays, so install from the newest (2026-11-11: the old folder put yesterday's winmm.dll back).
- Ruins are items: itemrules.xml has one, the **Goody Box** (type 0x21F). `Objects::init_item(TypeIndex, Coord x, Coord y)` 0x00653E00 (`ret 0xC`, `this` unused) makes one and returns its index in `items` (`Item **` at 0x00C0A110, count 0x00C0A104; `+8 & 1` alive); the map maker and `ScenarioEditor::add_item` 0x0099D500 put it in the middle of a WCoord cell (`wc * 768 + 0x180`). World cells: `[World + 0x134]`, 28 bytes each, row width `[World + 0]` (WCoords); word `+0` must not be negative (the editor's test), `+8` / `+0xA` are the first object's id / player of the cell's chain, every object's next one at `+0x2C` / `+0x2E` (players' object arrays at 0x00C0AB84 + 28 x player). The chain ends with id -1, or with id **-3 and the item's index** in the player word: the cell's item. `init_item` writes `-3, index` as the cell's whole chain, so in a live game (units standing there) cards.c puts the old head back and hangs the item on the last object. `ObjectsData::find_goody_at` 0x0065C040 walks that chain; `Unit::explore_goody` 0x005F9780 (this = the unit, `[unit + 9]` its player) takes the item at its cell (vfunc +0x90 on the item), clears the `-3` and bit 15 of the cell's word, and gives the resources.
- Pausing: `ScenarioFuncSet::pause_game` 0x009E5B70 / `unpause_game` 0x009E5BA0 (`this` unused; nothing in multiplayer) set / clear bit 0 of `[TurnControl + 0x10]` (`TurnControl *` at 0x00C06180, `is_paused` 0x009E5BE0) and pause the sound. `ScenarioFuncSet::get_current_age(const int &player)` 0x009EE920 (`this` unused): 1 Ancient .. 8 Information, -1 for no player.
- The setup's Time Limit combo is id 0x48 (`SetupWin + 0x21DC`, `Game + 0x3C`; the combo ids follow the Game bytes: id = byte + 0xC from Teams & Allies on). `SetupWin::update_interface` shows it only for the Time Limit victory (0x005B5F57: Victory's item == 4, then the combo's vtable +0x18 show, else +0x1C hide); survival.c's hook there shows it in the Survival setup. `ScenarioFuncSet::get_time_limit` answers -1 unless the victory is Time Limit, so the script gets the length from the DLL. A PullDown's items (64 bytes, `+0x34` id, `+0x38` flags) are left out of the open list when bit 0 of the flags is clear.
- Script functions used by the cards: `give_good(p, "Food", n)` gives resources (the Chess Exercise scenarios use it), `territory_owner(x, y)`, `stop_timer(name)` (the one-shot message timers are removed right after the DLL has seen them, so they do not pile up).
