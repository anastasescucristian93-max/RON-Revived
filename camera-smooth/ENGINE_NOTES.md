# Engine notes (camera-smooth DLL features)

Addresses are virtual addresses in `riseofnations.exe` (Steam EE, timestamp 6674863F), from `sbl/rise_z.map`. Engine notes for the Data Center are in `data-center/ENGINE_NOTES.md`, for per-nation art in `roman-buildings/ENGINE_NOTES.md`.

## Updates from the launcher (launcher_update.c, package\update.ps1, 2026-10-31)

- The launcher is its own process, patriots.exe (`LAUNCHER_TIMESTAMP`), and loads winmm.dll from the game folder too. Play starts riseofnations.exe and the launcher exits, so while the launcher shows, the game's files are free but winmm.dll is loaded by patriots.exe: the updater must wait for that process to end before it replaces the DLL. The plate's Update starts `RON_Revived_update.ps1 -WaitPid <launcher pid>` (CREATE_NEW_CONSOLE) and calls ExitProcess.
- The launcher's window is two: the background (layered, the PNG's size) and the controls' dialog 102 centred on it, owned by it (`GetWindow(dlg, GW_OWNER)`). layout.ini [slides] x, y, w, h is the picture's panel in background pixels; the plate goes over its bottom, placed from the dialog's centre and the owner's size (both move together when the window is dragged).
- `https://github.com/<repo>/releases/latest/download/<asset>` redirects twice (to the tag, then to a signed release-assets host); WinHTTP follows both by default. It is not the REST API, so it has no 60-an-hour limit. Before the first release with RON_Revived_update.txt it answers 404.
- The check reads only `version=` and, per part, the content hash and the zip size; the zips' SHA-256 is checked by the script. The content hash is over the files' paths and SHA-256 (build_package.py), not the zip's bytes, so rebuilding a part whose files did not change gives the same hash and players do not download it again.
- Tested 2026-10-31 outside the game: the check and the plate in a harness (local server: "1 of 3 parts changed, 9.4 MB"), and the script on a copy of the game folder (only core downloaded, a file left out of core removed, art and music kept in RON_Revived_files.txt). Not yet seen in the real launcher.
- `near` and `far` are macros in the Windows headers: not usable as variable names.

## Extras tray (launcher_extras.c, package\extras.ps1, 2026-11-05)

- The extras are parts of the pack like core and art, but optional: `build_package.py` EXTRAS (path starts), left out of the whole zip. The index names them (`extras=music`, `name.<id>=`, `desc.<id>=`) and an extra's line can list several zips (`<id>=<content> <sha> <bytes> <zip> <sha> <bytes> <zip>...`), for extras over GitHub's 2 GB per file. Older launchers and update scripts ignore `extras=` and the dotted keys (their patterns need `[a-z]+=` then three fields) and read only the first zip of a line.
- Installed = a line in RON_Revived_parts.txt [parts]. The updater (update.ps1 and launcher_update.c's count) skips extras that are not there; the whole install keeps the extras' files and their parts lines.
- The music's list goes with it: `mod_override\Data\sound.xml` and the translations mod's copies per language, `sound.xml.21` .. `sound.xml.31` (the game reads `Data\sound.xml.<language id>`). install.ps1's Get-Part must use the same starts as build_package.py: an exact `sound.xml` there once sent the five copies to core, and a whole install then deleted them.
- install.ps1 with `-Parts <extra>` must not count the version and parts files as part of the payload ("meta") when the payload has none: it deleted them as files the new version no longer has.
- `powershell -File` reads an argument `-` as a parameter with an empty name ("the value of argument name is not valid"): the placeholder for no zips is `none`.
- The tray is a layered popup owned by dialog 102 (above the launcher), drawn only where background.png is clear and left of the column's edge (the edge most rows of [extras] top..bottom have; the corner brackets stand 4 px further out), so it seems to come from behind the launcher.
- patriots.exe started by hand (not by Steam) loads `C:\Windows\System32\winmm.dll`, not the game folder's: no theme, no tray. Under Steam the game folder's is loaded. A test outside Steam needs the DLL injected (an early APC of LoadLibraryW on the suspended main thread works).
- Tested 2026-11-05 outside the game: the tray drawn off-screen by a harness that includes launcher_extras.c (every state), the index read from a local server in the injected launcher, and extras.ps1 on a copy of the game folder: whole pack, music installed (60 files), whole pack again (music kept, parts line kept), music removed (60 files out, empty folders gone, version file kept).

## Startup hang (ron_camera.c warm_up_bcrypt, 2026-10-30)

- Symptom since about 2026-10-21 (Steam forum "Game is not starting", players of the plain game): after Play, `riseofnations.exe` stays alive with no window, 0% CPU, ~46 MB; about half the starts. Windows 11 26200 with 32-bit `bcrypt.dll` 10.0.26100.9711 (KB5127647/KB5127648, 2026-10-13) and Steam `steamclient.dll` / `gameoverlayrenderer.dll` 11.15.70.27 (2026-10-21); the game files are unchanged. This PC has the same versions.
- Cause (stacks posted by kaustubhgc, Steam Support forum, 2026-10-29): a lock-order deadlock. The main thread's SteamAPI_Init loads `steamclient.dll` through the overlay's LoadLibrary hook; its DllMain (loader lock held) calls `tier0_s!SecureRandomBytes` -> `BCryptGenRandom` -> `bcrypt!LoadProviderEx` and waits for bcrypt's provider lock. A PartyWin.dll worker thread holds that lock inside `BCryptGenRandom` / `LoadProviderEx` and its `_LoadImage` -> GetProcAddress waits in `LdrpDrainWorkQueue` for the loader.
- `PartyWin.dll` and `PlayFabMultiplayerWin.dll` are loaded at process start (the exe imports `CrossplayProxy.dll`, which imports both). PartyWin imports BCryptOpenAlgorithmProvider / GenRandom / the hash calls and names only the SHA256 algorithm; PlayFab imports only BCryptGenRandom.
- Reproduced with a 32-bit test (`work/locktest/test3.c`): a thread calling `BCryptGenRandom(NULL, .., BCRYPT_USE_SYSTEM_PREFERRED_RNG)`, `BCryptOpenAlgorithmProvider(SHA256)` or `(RNG)` blocks for as long as another thread is inside a DLL load (an `LdrRegisterDllNotification` callback that waits), but only while bcrypt is cold. After one `BCryptGenRandom(NULL, .., SYSTEM_PREFERRED_RNG)` in the process, all three go through, even after any opened handles are closed: bcrypt's lazy setup is once per process.
- Fix: winmm.dll's DllMain makes that one call. The game imports winmm, so it runs during process start, when other threads cannot run yet (new threads wait for the process start to finish). Called under the loader lock with bcrypt cold, it loads in ~15 ms (`work/locktest/loadit.c`). The DLL imports bcrypt.dll (`-lbcrypt` in build.ps1).
- A test DLL whose DllMain waits on an event was removed by the PC's security software as it loaded (error 5, then 126). The DLL load notification route needs no extra DLL.

## Armageddon (armageddon.c)

- `Game::get_armageddon` 0x00594020 returns the number of nukes allowed. It is computed from `rules.xml` `ARMAGEDDON` (4), plus `ARMAGEDDON_PER_NATION` (1) times `game+0x6A0` and `ARMAGEDDON_PER_TEAM` (2) times `game+0x6A8`, then scaled for some game modes. The `Constants` fields are +0xD14 / +0xD18 / +0xD1C.
- `game+0x6E0` = nuclear detonations so far.
- `GameDaemon::process_victory` 0x00730EF0: `if (game+0x6E0 >= get_armageddon()) Game::defeat_all()`. The `jl` at 0x00730F1F skips it; the mod makes it a `jmp`.
- `Object::do_launch` 0x0064FE5E already refuses to launch a Nuclear Missile from a silo once `count >= armageddon - 2`. Other launches are not limited, so the clock can overshoot.
- `LeaderData::can_nuke` 0x006D53C0 (`get_units(0x13B) != 0`) is checked by `Group::action_flight`, the launch command.
- Nuclear unit types: 0x13B Nuclear Missile, 0x13C Nuclear ICBM (both at the Missile Silo); 0x13A Cruise Missile is not nuclear.

## Nuclear explosion look (NukeOut, not modded yet)

- The blast is drawn in code, not from the XML: `NukeOut::draw` 0x00926410 calls `draw_impact_flash` 0x00928990, `draw_shroom_top` 0x00926A00 (`art\nukecap.bh3`), `draw_shroom_stalk` 0x00926F70 (`nukestem.bh3`, `nukestalk.tga`), `draw_shroom_fire` 0x009274F0, `draw_dust_ring` 0x00927E90 (`nukedustring.bh3`), `draw_fire_ring` 0x009284E0 (`nukeglowring.bh3`), `draw_char_earth` 0x009277E0 (`nukescorchedearth1-4.tga`). `Nuke::add_nuke` 0x0092BA30 starts one, `Nuke::do_damage` 0x0092BC80 does the damage, `TerrainOut::terraform_for_nuke` 0x00869CA0 digs the crater (`nuke_crater_depth` 0xC0628C = 30.0, `nuke_crater_size` 0xC06290 = 3).
- Its tuning values are plain globals (BSS), written with constants by the `init` functions, then read every frame; `Nuke::registration` 0x00925EC0 lists them for the developers' parameter window. Overwriting them after `NukeOut::init` changes only the picture, so it cannot desync.
  - `NukeOut::init` 0x0092C9A0: screen tint during the blast `min_nuke_lum_r/g/b` 0xCBEDC4/0xCBEDC0/0xCBEDB4 = 0.3/0.59/0.11 (the grey weights: the world goes grey), `max_nuke_lum_r/g/b` 0xCBEDB0/0xCBEDBC/0xCBEDB8 = 0.7, `percent_to_min_lum` = 0.4; `smolder_num` 0xCBECC4 = 12 fires left burning, `smolder_dist` 0xCBECC0 = 310.
  - `NukeOut::init_impact_flash` 0x0092AAE0: `impact_total_frames` 0xCBED04 = 32, `impact_expand_frames` 0xCBED00 = 4, widths 500/600/0 (bright core) and 600/900/600 (halo), `impact_divisions` 50.
  - Also registered: `shroom_cloud_radial_start/end_scale` 0xCBED60/0xCBED5C, `shroom_cloud_z_start/end_scale` 0xCBED54/0xCBED50, `num_fire_particles` 0xCBED78 (max 250), `particle_width/height/size/percent`, `scorch_radius` 0xCBE6BC.
- The game does shake the camera (no shake/rumble symbol, but `Nuke::draw` calls `Camera::set_loc_adjust` 0x008438C0 with `sin/cos(t * 500) * 4 * envelope`), for every young blast wherever it is. Sounds: `soundtypes.xml` NUCLEARMISSILE ATTACK = `NuclearDetonation`, NUCLEARICBMMISSILE ATTACK = `SuperNukeHit` (`sounds\supernuke.wav`, `nuclearicbm.wav`).

## Nuclear weapons (nukefx.c, 2026-10-27)

Found with three research passes over the disassembly on 2026-10-27; the facts that matter are here. Nothing below has been seen in game yet.

### The flash on the screen
- In a match the blast's screen effect comes only from `Nuke::draw` 0x0092B370, called by `Scene::render` at 0x008B3B0C (`E8` rel32) when `scene+0x202 & 8`. `NukeOut::draw` 0x00926410 does the same writes but only for the Conquest map (`ConquestWin::draw_nuke_shroom`, `Nuke::draw_ctw`).
- Per blast, t = (`game+0x550` - start) / `[0x00C0A890]` (110), only while t <= 1: a = t < 0.05 ? (t/0.05)^2 : 1 - min(1, (t-0.05)/0.45)^2; b = t < 0.05 ? (t/0.05)^2 : min(1, (t-0.05)/0.65)^2. It writes the tone mapper (`graphsys` vtable +0xBC, `+4` dirty byte): `+0x0C` = 32 a^2 (the white flash), `+0x1C` = b (saturation, the grey world), `+0x28` a Color `0x??0EC1EE` with alpha (0.4 (1-b))^2 * 255. Nothing tests where the blast is. At rest 0 / 1 / alpha 0. Then the camera shake (`Camera::set_loc_adjust` 0x008438C0, `sin/cos(t * 500) * 4 * envelope`, also for every blast wherever it is), then `TerrainOut::is_region_visible` decides whether the shroom is drawn.
- Tone mapper fields named by `Scene::registration` (0x008BCD85 on): `+8` Exposure, `+0x10` White Point, `+0x14` Bloom Threshold, `+0x18` Minimum Luminance, `+0x24` Bloom Tightness, `+0x20` one more (string 0x00AF3184). `Scene::render` applies it right after Nuke::draw (0x008B3B47). Shader `shaders\ps_tonemap.hlsl` (cbuffer `ToneMapData`, b4).
- Camera `+0x304 / +0x308` (floats) = the screen centre on the ground in world units; `+0x2F0` the zoom distance (18544 at level 5).

### Blasts
- `Game::do_frame`: `Objects::process_all` (0x0059246F) then `Objects::inc_time` (0x00592474), which calls `Nuke::do_damage` 0x0092BC80 and then `Ammo::inc_time` 0x0067D380 for every ammo -> `Ammo::do_damage` 0x00678060 -> `Nuke::add_nuke` at **0x00678516** (`E8 15 35 2B 00`, its only caller). So a blast is added inside the simulation on every machine. The sound inside add_nuke uses `SoundGlobal::random`, its own generator.
- `Nuke::add_nuke(Coord x, Coord y, Coord r0, Coord r1, int player, int id)`, thiscall, `ret 0x18`, `this` unused: x, y = `ammo+0x18/+0x1C`; r0 = 100; r1 = `TypeData(missile)+0x200` (SPLASH) x 192 (1920 Nuclear Missile, 3840 ICBM); player = `ammo+0x3C`; id = `ammo+0x40` (the missile). Arrays (`TexArray`s 0x00C0A7C0 / 0x00C0A7DC, data at +0x10): count `[0x00C0A7FC]`, `[0x00C0A7D0]` x, y floats, `[0x00C0A7EC]` **(r0, r1), the damage radius pair, not a second position**, `[0x00C0A808]` start time, `[0x00C0A824]` player, `[0x00C0A840]` missile id. `[0x00C0A884]` = 10, `[0x00C0A888]` = 30 (damage wave delay / growth), `[0x00C0A890]` = 110, `[0x00C0A88C]` = 7 (draw mode). Not in saved games.
- `Nuke::do_damage`: the wave does damage from start+10 to start+40 (radius 100, then to r1 over 30 frames, factor 256 - d*256/r1, through the missile's `Object::do_damage`, so kills go to the nuke's owner); a blast is swap-removed at start + 110 + 0x140 (430 frames, 28.7 s; the `add ecx, 0x140` at 0x0092BCD4); **Armageddon `inc [game+0x6E0]` at 0x0092BF09** when the age crosses 110.
- Before the nuke branch, `Ammo::do_damage` checks the target territory's owner for type 0x2B5 (the Missile Shield, tech 0x243, inferred): strings 84/85, sound 0x9A, `Ammo::close`, no blast.
- Crater: `TerrainOut::terraform_for_nuke` 0x00869CA0 (from add_nuke) lowers the corner heights `terrain+0x4A4` by 30 within `nuke_crater_size` and lists the tiles at `terrain+0x4BD4`; nothing raises them again during a match, `rebuild_nuke_craters` re-digs them on load. **The crater stays the whole game.**
- Scorch: `Nuke::draw_underlays` 0x0092B2F0 (from `Scene::render` 0x008B3732, gate `scene+0x200 & 1`) calls `NukeOut::draw_char_earth` 0x009277E0 per blast (x xmm1, y xmm2, t = age / 110 xmm3, no stack args, plain `ret`, keeps ebx/esi/edi, ecx unused), drawn only when `[0x00C0A88C]` is 0, 7 or 9. Fade: s = age / (110 + span), full to 0.75, then 1 - 4(s - 0.75); the span is the `add eax, 0x140` at 0x009279A4 (picture only).
- Smoke: `NukeOut::graph_do_damage` 0x00925970 spawns `smolder_num` (12) emitters of particle system "NUCLEAR SMOKE" at age 66 with a local random generator; they emit for its `game_frame_emit_time` (11000 ms in effects_graphics.xml; system field `+0xAC`). That system is used nowhere else.

### Nukes in flight
- A launched Nuclear Missile / ICBM Unit fires an **Ammo** at once and dies (`Object::fire_ammo` 0x0064C8B0, then `Object::die`, in `Unit::do_air_attack_ground` / `do_strafe`). The flight is the Ammo: array `objects+0x11C` (count `[objs+0x120]`, `Ammo **` `[objs+0x12C]`, objs = `*0x00C0618C`), in use when `byte [a+4] & 3`, slots reused. Fields (plain ints): start `+0x0C/+0x10/+0x14`, end `+0x18/+0x1C/+0x20`, `+0x24` cur_time, `+0x28` total_time (frames), `+0x3C` owner, `+0x40` the missile's id, `+0x48/+0x4C` target player / id, `+0x68` Spline (one point per frame, count `+0xD8`, float3 data `+0xE4`). A nuke: the missile slot `[[objs+0x14+0x1C*who]+4*o]` (dead, but it keeps its TypeData) has `TypeData+0x1E4 & 0x8000000` and type 0x13B / 0x13C (as `ObjectsData::count_nukes_in_flight` 0x00658490 tests).
- `Ammo::inc_time`: `++cur`; an object-targeted ammo can end early (homing: the spline point within the target's radius); at `cur >= total` `AmmoOut::graphic_finish` (picture), then `Ammo::do_damage` unless `byte [a+4] & 0x10`.
- **`Ammo::close()` 0x006791A0** (thiscall, no args, `57 8B F9 8B 47 68 C6 47 04 00`) frees the slot and the spline: no sound, no message, no damage. Called from the `Objects::process_all` post-hook (before inc_time), the nuke never reaches do_damage: no blast, no crater, no Armageddon count.
- Anti-aircraft cannot shoot nukes in the game: the flight is an Ammo, not an object, and `ObjectData::valid_target_const` 0x006472C0 (vtable +0x138) rejects missile targets anyway (0x006476F2). Nothing to block.
- Missile Silo: type 0x208 (building 106). Units inside: list head `short [b+0x28]` / `byte [b+0x3E]`, each unit's `+0x28/+0x3E` the next; a unit's container `short [u+0x82]` / `byte [u+0xB4]`. Launch queue `[b+0x44]`, countdown `word [b+0x7A]` (`Build::do_missile_launch` 0x00622670). Its panel: the launch button at (2, 0).
- A building's production queue: `BuildData` (object vtable +0x3C) `+0x88` = `BuildQueueData`: `[0]` count, `[1]` items, 0x14 each, short type at +4 (`BuildQueueData::get_queue` 0x00630670).

### Damage like attrition
- `Unit::suffer_attrition` 0x005E1A10 hits through the virtual `take_damage` (vtable +0x16C, `Object::take_damage` 0x00652020, `ret 0x24`): single unit `(1, 0, 1, -1, 1, 0x55555555, -1, -1, 0)`, squad `(0, n == 3 ? 6 : 16 / n, ...)` with n = `UnitData::curr_uber_size(0)` 0x0060A760. a1 whole hit points, a2 sixteenths (carried in `+0x3B`); a5 = 1 is quiet (no AI alarm, no "in danger", no use of the game's random); a7 / a8 = -1: nobody is credited. Each soldier of a squad is its own object and dies at hits / n.
- `[unit+0x9E]` is the **period** of the attrition hits, used as `(time + id) % period == 0` (`Unit::process` 0x006117C8), not a countdown. Type `+0x218 == 2` is DOMAIN Air (aircraft and missiles), worth re-checking against the attrition notes above.
- 15 simulation frames a second (rules.xml); the game's own minute is 900 frames.

### Underlays (flat textured quads on the ground)
- Types from `effects_graphics.xml` `<UNDERLAYS>` (the code uses the first 20 by index, so new ones go at the end): `Underlays::init_class` 0x008E18F0 counts them in `[0x00C0A46C]`. Type table count `[0x00C8C6FC]`, data `[0x00C8C708]`, 0x14 each: +0 tu, +4 tv, +8 twidth (floats), +0xC growth, +0xD render state, +0xE tex0, +0xF tex1, +0x10 pass. Textures in the section's own `<TEXTURE>` list (tex0 counts from 0).
- Instances: `[0x00C8C720][type]` = `ObjectArray<UnderlayStruct>*` (+4 count); add with `ObjectArray<UnderlayStruct>::add(const UnderlayStruct &)` 0x004A9D20 (thiscall, `ret 4`). UnderlayStruct, 0x20 bytes: x, y, z floats; binary angle (2^32 = 360 degrees); remaining ms; total ms; width (world units); two shorts -1. Growth 1: alpha = 10 * remaining / total under a tenth, else 1. `Underlays::draw(0)` (0x008B3762) runs before `Underlays::inc_time` (0x008B3A3A, subtracts the frame's ms, removes the expired), with no visibility test; `Underlays::add` 0x008E1410 adds only points the local player sees, so own instances go in with `ObjectArray::add`.

### nukefx.c
- Flash: the call at 0x008B3B0C goes to `c_nuke_draw`, which calls Nuke::draw, then rewrites the three tone values from every blast with t <= 1, each scaled by its distance to the screen centre (smoothstep from `flash_full_tiles` to `flash_zero_tiles`, both times the zoom distance / 18544, clamped 0.5-3), the strongest kept. The camera shake is left alone. Then it writes the underlays (below), drawn the next frame.
- Interceptors (simulation, from airdrop.c's `Objects::process_all` hook): the nuke-fx data makes unit 337 "SAS" (type 0x183) the Interceptor (WHERE Missile Silo, the Cruise Missile's fields, GRAPH SCHWARZENBERG, whose graphics entry is a copy of the Cruise Missile's). Each frame every living Interceptor is counted for the silo it is in (get_inside, else the nearest own silo), at most 2, and disbanded. For each nuke Ammo not yet targeted: every enemy silo (`LeaderData::is_enemy`) with an Interceptor and the nuke's current ground position (the straight lerp start -> end by cur / total) within `interceptor_reach_tiles`; the meeting frame k is the first with (k - 15) * v >= distance(silo, nuke at cur + k) and cur + k < total, v = `interceptor_speed_percent` of the nuke's ground speed (at least 64 world units a frame). The earliest meeting wins; at that frame, if the slot still holds the same nuke (owner, missile id, end point), `Ammo::close` and the shield's sound 0x9A for the two players involved. The silo's Interceptor button is disabled in `BuildOut::make_options` when the silo holds and makes 2; panel.c shows the count on it.
- Radiation (simulation): the call at 0x00678516 goes to `rad_add_nuke` (records x, y, r1 and the time, then calls add_nuke). Every 15 frames, for `radiation_seconds`, every living unit on the map within r1 (not decoys, not DOMAIN Air) gets `take_damage` as attrition with nobody credited: max hits (vtable +0x11C) x `radiation_percent_per_second` % x (time left / duration), in sixteenths, divided by the squad's soldiers left.
- Underlay orientation (`Underlays::draw` 0x008E0080, read 2026-11-08): for an instance at c = (x, y), half width h and angle a, with U = (cos a, sin a) and P = (-sin a, cos a), the quad's corners are c - hU + hP, c - hU - hP, c + hU + hP, c + hU - hP, with tex0 coordinates (u0, v0), (u1, v0), (u0, v1), (u1, v1) (u0 = tu / texture width, u1 = (tu + twidth) / width, the same for v with tv). So the texture's +u runs along -P = (sin a, -cos a) in the world and +v along U: a picture pointing along +u points at the world angle a - 90. (tex1 takes other corners: (0, 1), (1, 1), (0, 0), (1, 0).)
- Drawing: underlay types NukeTarget (one blade of the sign), NukeHaze, NukeTargetGlow (the blade's glow), NukeCore and NukeCoreGlow (the disc in the middle, 2026-11-08) (nuke-fx's effects_graphics.xml, textures 14-18, found at run time by tex0; the glows use the game's "Shockwave Blend", taken to add light like the Flash / Healing underlays, not checked in the code; drawn over the shapes with a pulsing alpha). Each frame the instance lists are emptied and refilled: over every nuke's end point the disc and three blades at the world angles 90, 210 and 330 degrees (drawn at angle phi + 90, see above), all at width 1.34 r1, the blades pushed out by 0.75 r1 (1 - progress) along their angle (until 2026-11-08: one sign, width 2 r1 (1.5 - 1.1 progress), turning 25 degrees a second); two haze layers turning opposite ways over each young zone, fading in over a second and out over the last quarter.
- Scorch: the span at 0x009279A5 becomes (110 + 0x140) x `scorch_percent` / 100 - 110, and the call at 0x008B3732 goes to `c_nuke_underlays`, which calls the original and then draw_char_earth itself for recorded blasts already dropped from the game's list (age 430 .. 430 x percent / 100). The game's list and its order are untouched, so it is safe in multiplayer whatever each player sets.
- The smoke (NUCLEAR SMOKE) emits 3 times as long through the nuke-fx effects_graphics.xml (33000).
- A new game (the game time going back or jumping) clears the tables; a loaded game fills them from the save (below).
- Faster and lighter (2026-11-05, the user: out of the silo at once, 3 to 5 times the nuke's speed, a light explosion in the air and a faint light, as if it happened off the screen): `LIFTOFF` 4 frames (was 15), `interceptor_speed_percent` 400 (250, the old default kept in earlier installs' ini, reads as 400), the airburst's `add_explosion` scale `interception_burst_size` (2, was 4). ## How the computer commands units, and keeping your orders (assist_orders.c, 2026-10-30)

- **Human orders** are commands: `CommandPackage::process(Command *)` 0x0094A700 (thiscall, `ret 4`, one caller: `process_all` at 0x0094C6D4) switches on `byte [cmd]` (jump table 0x0094B5F4, 0x52 entries). 0 = group: `process_group` 0x0094A0C0 (`cmd+1` count, `cmd+2` owner, shorts from `cmd+3`; it also keeps `CommandPackage::last_objects_received` 0x00CBEEB0 short[sender][128] and `last_num_received` 0x00CBEE88) puts the units in a persistent group and leaves its index in `package+0x0C`. The unit orders that follow act on that group (`imul ecx, [pkg+0xC], 0x9D4; add ecx, [0x00E85F20]; call Group::action_*`). Unit order types: 2 stance, 3 form, 4 attack, 5 siege attack, 6 swarm around, 7 move to, 8 move near, 9 attack ground, 0xA patrol, 0xB launch patrol, 0xC halt, 0xD transport, 0xF board ship, 0x10 repair, 0x11 trade, 0x13 gather, 0x14 garrison, 0x17 spell, 0x19 build, 0x1C flight, 0x1E follow, 0x1F guard, 0x23 recall, 0x24 scramble (others: 0x12 city gather, 0x15 disband, 0x16 gather point, 0x18 queue up, 0x1B alarm, 0x25-0x2F diplomacy and market, 0x44 chat, 0x48 camera). `package+4` = the sender; `game+0x77+sender*0x8C` its player. ## Who plays a nation: human or computer (assist_panel.c)

- `[leader + 0]` (leaders 0x00E3A390, 0x6EEC each, index = player 0-7 as `Console+0x298`): bit 0 = the player exists, bit 2 (4) = a human plays it; clear = the AI plays it. Bit 3 (8) keeps the units' AI flag when switching to human.

- The console commands `computer <name>` / `human <name>` are in `ConsoleWin::run_cmd` 0x007D6A70 (command id 0x31 = human): they flip bit 2 of the leader (0x007DC9B0 / 0x007DCA54) and the unit flag of every unit (`Units::operator[]` 0x0043E6E0), and on "human" also refill hotkey group 10 with a Group (`HotKeyGroups::copy_group`), nothing more. The AI needs no other set-up: it plans for every leader without bit 2.
- `ScenarioFuncSet::change_to_ai(const int &player)` 0x009E5D20 and `change_to_human` 0x009E5C80 (thiscall, `ret 4`, `this` unused) do the same flips; their player counts from 1 (`dec ecx`). ## Attrition (attrition.c)

- `Unit::process_attrition` 0x005E11A0 decides whether a unit stands in enemy land without supply and sets `[unit+0x9E]` (word, frames until the next hit; only lowered, never raised while counting) to `Constants+0xD3C` (rules.xml `ATTRITION`, 48 frames; `Constants::init` reads it at 0x005700F6) times `UnitData::get_attrition(owner)` 0x00608FD0 / 256, at least 1 (0x005E193D..0x005E1973).
- `get_attrition` returns a factor in 1/256: 256 / the territory owner's attrition strength (`[leaders + owner*0x6EEC + 0x7F0]`; 0 = none), made larger (= slower attrition) by the Forage / Supply / Logistics techs (`Constants+0x1E8`, `+0x1EC`), halved for citizens 0x3D / 0x3E / 0x190 and for siege (`UnitType+0x218 == 2`), and lowered by the age difference (`Constants+0x1F0`, the 25 % per age of `ATTRITION_AGED_UP`).
- `Constants+0xD34` and `+0xD38` are the two 8-frame special cases (`PEACE_ATTRITION` at peace, `ASSASSIN_ATTRITION`), written straight into `+0x9E`.
- The hit itself: `Unit::suffer_attrition` 0x005E1A10, called from `Unit::process` (0x00610D35, 0x006117FE) when the count runs out: `take_damage(1, 0, ...)` for a single unit, `take_damage(0, 16 / soldiers, ...)` sixteenths for a squad (6 for 3 soldiers), attacker -1. It also shows the "attrition" message to the local player while `[leader + 0x1F8]` is 0, then sets it to the game frame (`process_attrition` keeps its own 0x384-frame timer for the border message in `[leader + 0x1F4]`).
- The mod: `mov eax, [eax+0xD3C]` at 0x005E1942 (8B 80 3C 0D 00 00) jumps to a stub that returns `ATTRITION * 100 / attrition_percent`, at least 1. Simulation: every player needs the same value.

## Veteran ranks (ranks.c)

Found 2026-10-26.
- What a saved game keeps of an object: `SubObject::walk_data` 0x006621D0 walks the raw bytes `+0x8..+0x9` and `+0x9..+0x18`, `Object::walk_data` 0x00647830 `+0x20..+0x42` (max hits `+0x20`, hits lost `+0x24` among them), `Unit::walk_data` 0x0060CF40 `+0x48..+0xB7` (then the path stack `+0xB8`, the orders `+0xC8`, the Guys `+0xE4`). The DataWalk's first virtual is `walk(start, end)`.
- Every byte of `+0x48..+0xB7` is used by the unit classes (scan of all Unit / UnitData / UnitOut / Animal methods). But no instruction in the exe touches **bits 20-31 of `+0x6C`**: no `test/and/or/xor` with a memory operand on `+0x6C` (bits used there: 0x0007FFFD), and no register read-modify-write of `+0x6C` whose mask reaches those bits. The read-modify-writes in `Unit::process_cloak`, `Unit::process` and `Unit::do_idle` keep the other bits. `UnitData::UnitData` and `Unit::init` zero the word for a new unit. `Unit::set_type` (line upgrades) changes the type in place and keeps it. The mod keeps the experience there (12 bits).
- Rounding (2026-10-27): experience per hit is applied x victim cost x 256 / (victim max hits x attacker cost). Against buildings (Fort 2000-4600 hits, cost 40 in tens; Red Fort attacker counted at 150) one hit is worth about 0.2 and was truncated to 0, so the user's Red Fort shelling a Fort never gained. ranks.c now computes it in 1/65536 and carries the remainder per attacker (`g_xfrac`, by the captain's or the building's id; in memory only, so a loaded game loses at most one unit of it).
- Level 10 (2026-10-27): the experience is 12 bits (bits 20-31 of `+0x6C` for units; for buildings the byte `+0x65` x 16 plus 0-15 in memory), so at most 0xFFF = 4095 / 256 = 16 units of the same cost destroyed. Level 9 is 3456, so level 10 sits at the maximum, 4095; a level 11 would need a wider store (no free bits left in `+0x48..+0xB7`) or coarser units, which would change the meaning of the experience in existing saved games.

## Unit facing (facing.c, patched 2026-10-26)

Why units do not turn smoothly and aircraft snap from angle to angle. Found 2026-10-24.

- Angles are 32-bit binary angles (a full circle = 2^32) in `Guy` (the unit's 3D model, `[unit+0xF4][0]`):
  - `+0x18` = current angle;
  - `+0x1C` = angle at the previous simulation tick;
  - `+0x64` = target angle.
  - `Unit+0x50` is the unit's own copy.
- `Guy::move` 0x005D9240 (from `Guy::process`) copies the current state into the previous one every tick: x/y/z `+0xC..+0x14` to `+0x68..+0x70`, angle `+0x18` to `+0x1C`.
- `Guy::turn_towards` 0x005D9720 turns by `GuyData::turn_speed` per tick, then `Guy::do_turn` writes `+0x18`. Under 0x2222220 (3 degrees) from the target it jumps straight to it. `turn_speed` returns 0x80000000 (a half turn in one tick) for a standing unit with flag `+0x9A & 0x10`.
- `Guy::set_angle(angle, snap)` 0x005D9010 always writes `+0x64`. With `snap = 1` it writes **both** `+0x18` and `+0x1C`, which removes the interpolation for that tick. Ground movement (`Unit::set_angle(a, ?, 0)` in `move_step`, `fight`, `do_guard`...) passes 0.
- Drawing: `GuyData::get_render_angle` 0x005DE570 = `prev + shortest(cur - prev) * f`, with `f = game+0x854` (`TurnControl::get_delta_percent` 0x00957950, the fraction of the current simulation tick, set in `Game::calc_graphic_resolution`). Position (`get_render_x/y/z`) and bank/pitch interpolate the same way.

Cause 1, all units: `GuyOut::draw` 0x005DC490 (call at 0x005DC87B, same pattern in `draw_shadows` at 0x005DC41B) passes the interpolated angle through `fast_angle_to_degrees` 0x00A28F70.
- It is a 256-entry table indexed by the top 8 bits (`sar 0x18`). Each entry is the INTEGER `angle_to_degrees(i << 24)`: 0, 1, 2, 4, 5, 7...
- The result is truncated again (`cvttss2si`), +180, mod 360, then `fast_half_degree_to_cosine/sine` 0x00A29010 / 0x00A29110 (tables per whole degree) give the quaternion.
- So a model only has 256 facings, with uneven steps of 1 and 2 degrees. A slow turn (ships, units at close zoom) moves in visible ticks.

Cause 2, aircraft: `Unit::do_air_physics` 0x005E86D0 sets the angle with `Guy::set_angle([unit+0x50], 1)` (push 1 at 0x005E8C25), so `prev == cur` and `get_render_angle` returns the tick's angle unchanged. The plane's facing changes only once per simulation tick (`TurnControl::get_frame_timing`), in steps of `Unit::air_turn_speed` (at least 0x5B05B0 per tick).

Possible fix:
1. Render only: replace 0x005DC880..0x005DC8E3 (and the same block in `draw_shadows`) with exact float cos/sin of the half angle. Store the cosine at `[ebp-0x50]`, leave the sine in xmm0, and check that `[ebp-0x10]` is not read later. This is multiplayer safe.
2. Aircraft: either keep `+0x1C` from the snapshot (write only `+0x18`; this touches simulation state, so check that `+0x1C` is not in checksums or saves), or keep a render-side table per Guy of the last two tick angles and interpolate there.

What was done (2026-10-26, render only, the second way for aircraft):
- `GuyData::get_render_angle` 0x005DE570 is a leaf (thiscall, ecx = Guy, eax = result; clobbers ecx, edx, xmm0) with only two callers, `GuyOut::draw` (0x005DC87B) and `GuyOut::draw_shadows` (0x005DC41B), so replacing it changes nothing in the simulation. Its interpolation: `diff = cur - prev` (unsigned); above 0x80000000 it takes `~diff` and turns back after the multiply, i.e. the shortest way round; times `float [game+0x854]`, truncated.
- Game time `[game+0x550]` is incremented only in `Game::do_frame` (0x005924BF, `inc`), the same frame in which `Objects::process_all` moves the Guys, and nothing is drawn in between, so it is a clean tick counter for a render-side "angle at the previous tick" table. facing.c keeps one per Guy pointer (4096 hashed entries) and uses it only when `+0x18 == +0x1C`; a Guy not drawn at the previous tick, or a time that went back (a loaded game), starts over without interpolation.
- `fast_angle_to_degrees` 0x00A28F70 (ecx in, xmm0 out): `table[(angle >> 24) & 0xFF]`, the table holding the integer `angle_to_degrees(i << 24)`, i.e. the unsigned angle times 360 / 2^32, truncated. `fast_half_degree_to_cosine/sine(int d)` 0x00A29010 / 0x00A29110 (ecx in): `cos/sin(d * 0.5 * pi / 180)` from 360-entry tables.
- In `GuyOut::draw` the block 0x005DC880..0x005DC8E3 takes eax = angle and leaves the cosine at `[ebp-0x50]` and the sine in xmm0; the quaternion built after it is (0, 0, s, c) at `[ebp-0x28]`. `[ebp-0x10]` (the degrees) is written again before its next read (0x005DCCEF), and xmm3..xmm7 are written before they are read after the block. The patch jumps from 0x005DC880 to a stub (fild / fmul / fsincos on the angle's top 24 bits: half angle + 90 degrees, or - 90 from 180 degrees on, which is the game's `+180 mod 360`) and back to 0x005DC8E3.
- In `draw_shadows`, `call fast_angle_to_degrees` at 0x005DC422 goes to a stub returning the exact degrees; the code after it computes `180 - degrees` (`[ebp-0x64]`).

## Fog of war on the terrain (fog.c)

- `TerrainVis::fill_fog_texcoords(ft, code)` 0x008B19F0 reads a 4x4 block of the bordered fog grid (`[0xE8A894]`, stride `[0xE8A79C] + 2`): rows `2*ty .. 2*ty+3`, bytes `2*tx .. 2*tx+3`, i.e. real cells `2t-1 .. 2t+2`. Vertex values come from sums of 2x2 cells through the table at 0x00AF2DF4 (2-cell sums are indexed `*8`, so they count double).
- With `code == 0` (fade), it first reloads `FT_CUR` (`ft+0x64`) from the terrain's current per-vertex fog values: `terrain = [0xC06218]`, buffer `[[terrain+0x1A80] + [terrain+0x1AD0]*4] + 0x10`, 8 bytes per vertex, row stride `[[0xC061D0]]*32 + 8` bytes (4 vertices per tile, plus one). Then it writes `FT_DEST` (`ft+0xC8`) and `FT_VEL` (`ft+0x12C`), and sets `ft+0x19C = 1`.
- The fog texture comes from `Data/tilesets.xml`, `<FOGTEX><TEXTURE file="./art/fow_fade.tga"/>`: 14 tilesets use `fow_fade.tga`, 3 dark ones `fow_fade_dark.tga`. Both are 256x1 32-bit TGAs (RGB black, alpha is the fog). `fow_fade` falls almost linearly from 255 (t = 0, unexplored) to about 76 at t = 2/3 (explored), then 56 at t 0.75 and a cliff to 0 by t 0.83. `fow_fade_dark` is about 18 at 2/3 and reaches 0 near t 0.8, no cliff.
- The fog texcoord is interpolated linearly across the terrain triangles and the ramp is read per pixel, so any cliff in the ramp gives a sharp line between vertices, whatever the vertex values: smoothed vertex values with the game's ramp showed as a sawtooth along the triangles at the edge of vision. A ramp that is linear where the vertices fade makes the pixels interpolate the alpha itself. fog.c writes both ramps, straight from t = 2/3 to 1, to `%TEMP%\RON Revived\` and serves them with `override_redirect` (needs `file_overrides`, but not a `mod_override\` folder).
- Teeth at the edge of vision that remained with the straight ramp (seen 2026-10-29 at the closest zoom, about one tooth per row of vertices): vertices on a cell boundary used a 4-tap Gaussian and vertices on a cell centre a 5-tap one, cut at different distances, so every other row was blurred slightly differently; `fog_edge=0.4` then squeezed the whole visible band into less than one vertex step and turned that small difference into teeth. Now both integrate the Gaussian over each cell inside the same window (3 cells from the vertex, `FOG_R`), and the defaults are `fog_blur=1.0`, `fog_edge=1.0`. A cell now reaches vertices up to 3 cells away, so a cell change invalidates 4x4 tiles (k-2..k+1 for cell 2k, k-1..k+2 for cell 2k+1).
- The fog grid values only feed the ground. Which units and buildings are shown is decided elsewhere, so a wrong fog texcoord shows as ground that is black or clear while the objects on it are drawn correctly.
- `Scene::render` 0x008B3270 calls `Camera::check_zoom` at 0x008B3342. `[camera+0x28C]` (set by `Camera::outdate` 0x00844B80) gates only the recomputation of the sprite scale factors `scene+0x2F8/0x2FC` there, not the terrain.
- `Camera::check_scroll` sets `scene+0x22D = 1` (0x00844503) when the integer camera position changes; that rebuilds the terrain's visible set. The original `check_zoom` (0x00843C30, steps 0x00843840 / 0x008449E0) never sets it. The flag is cleared with the dword `scene+0x22C` at the end of a scene function (0x008B3DF2), so a byte-displacement search for 0x22D finds no reader.
- Symptom when the visible set is stale after a smooth zoom: part of the screen (bounded by a slanted line, the edge of the old view) shows black ground while objects draw normally, until the camera moves. Fixed by setting the flag when the zoom settles and every 10 % of distance.
- **Correction (2026-10-30): nothing reads `scene+0x22D`.** The only byte access in the exe is the write in `check_scroll`; no word / dword read of `+0x22C` exists in the render code either (only `post_update_screen`'s clear). What rebuilds the ground is in `TerrainOut::render` 0x008558B0: after `inc_fog_time` it takes the rebuild branch (`TerrainVis::set_zoom`, `Roads::generate`, ..., `determine_frustum_intersect` 0x00854770, `add_visible_wcoord`, `set_pending_wcoords`) when byte `scene+0x22C`, dword `camera+0x28C` or byte `scene+0x229` is set (tests at 0x00855A8F, 0x00855B94, 0x00856245). `camera+0x28C` is written 1 by `Camera::outdate`, `set_loc(int,int,int)` 0x00844A60, `set_loc_adjust`, `set_zoom_to`, `set_dir`, `set_in`, `zoom_in_times`, `zoom_out_times`, the minimap, and cleared only by `Scene::post_update_screen` (0x008B3DD7), at the end of each frame. So the zoom fix worked through the `outdate` that `mark_moved_ex` calls, not through `+0x22D`.
- Minimap: `WorldMap::update_world_map` 0x008D2BA0 moves the camera with `Camera::set_loc(x, y, 0)` (0x008D2CA8, clamped to the map, skipped with `camera+0x35C & 4`) and sets `+0x28C = 1` again (0x008D2CB3). It is called from `WorldMap::on_left_down` (the click) and every frame from `Game::loop_render` (0x00591C08, after `Window::update_screen` and before `check_scroll`, for a held drag).
- Black ground after a minimap jump (seen 2026-10-30): the new view's upper part black with sparse ground-coloured pixels, a horizontal edge, objects drawn; not seen whether it lasts until the camera moves. Which of two causes is not proven: the outdate cleared by `post_update_screen` before a render saw it, or a rebuild that did not fill the whole new area in one frame (`TerrainVis` streams geometry into cache blocks: `get_free_block` 0x008B0CE0, `squeeze_cache`, `set_pending_wcoords` 0x008B26F0, and `add_visible_wcoord` 0x008B2EB0 sorts tiles into 3 buckets by age). `settle_ground` in ron_camera.c covers both: at the end of `c_check_zoom` (before `TerrainOut::render`) it compares the camera's position, distance, tilt and direction with the last frame and keeps `+0x28C` set for 0.3 s after any change. It logs the first 5 changes that came without an outdate ("ground: camera moved ... without an outdate"); such lines would prove the first cause.
- `add_visible_wcoord` fills a newly added tile's fog at once (`fill_fog_texcoords(ft, 1)` at 0x008B2F6A, bucket 1 only, unless `CoordInfo+0x70 == -2`) and writes it to the terrain vertices; `TerrainOut::inc_fog_time` 0x0086D8E0 fades the tiles of its transition list (`+0x6A74`, count `+0x6A68`) with `fill_fog_texcoords(ft, 0)` at 0x0086D9AC, stepping `FT_CUR` by `FT_VEL` only when the graphics byte `[[graphsys+0x13C]+2]` is set (else it jumps to `FT_DEST`).

## Ground vertex streams and the 16-bit limit (ron_camera.c `ground_guard`, 2026-11-01)

- TerrainVis is `[0x00C06218] + 0x533C` (TerrainOut::render calls `set_zoom` on `edi + 0x533C`, edi = `MiscAccess::terrain`). `+0xC` = number of streams (buckets; the last 6 are special ones), `+0x4` = LOD: TerrainOut::render passes 0 at camera level 6, 1 at level 5, 2 otherwise. Vertices per tile by LOD (`+0x10/+0x14/+0x18`, set in the constructor 0x008B215F): 25, 25, 9 (always 9 with graphics detail `graphsys+0xE0 >= 3`).
- Per stream: vertex buffer `[+0x24] + s*8 + 4`, block stamps `[+0xF4] + s*0x1C` (SimpleArray<DWORD>: +4 count, +0x10 data), block owners (CoordInfo *) `[+0xF8] + s*0x1C`. `+0xFC` = stamp of the last rebuild (`game+0x848`, written at the end of `set_pending_wcoords(0)`); a block whose stamp equals it holds a tile in view.
- `get_free_block` 0x008B0CE0 scans from the stream's hint `[+0x1C][s]` (reset to 0 at each `set_pending_wcoords`) for a block whose stamp is neither `+0xFC` nor this rebuild's; at the end of the array it grows it by min(pending, 75) blocks, resizes the vertex buffer to 25 vertices a block, and rebuilds the stream's whole index arrays (`temp25` with offsets `block * 25`, `temp9` with `block * 9`, through `SimpleArray<unsigned short>::append_with_offset`, an **unsigned short** offset). `move_data_to_stream` writes a tile's vertices at `block * 25` whatever the LOD; `build_index_buffer` 0x008B0300 adds `block * 25 - first` to each block's indices, also as unsigned short.
- So a stream with more than 65536 / 25 = 2621 blocks wraps: its tiles index vertices of tiles far away, drawn as long parallel streaks across the screen, down to the bottom and beyond the map edge (seen 2026-11-01 on a desert map at the extra zoom out, 2559x1599: one ground texture filled the view). The huge triangles are slow to draw, so the game stuttered too. The game's own levels never got there; the step farther out shows 2.25 times the tiles of level 4.
- Blocks in view keep their index, so once a stream has grown past the limit the streaks stay after zooming back in, until the LOD changes (`set_zoom` with a new value resets the hints and `+0xFC = 0x7FFFFFFF`) or the ground is cleared.
- `set_zoom(5)` (4 and 5 are never stored as the LOD) does the reset and then `TerrainVis::clear` 0x008B1480, which shrinks every stream's block array back to 200 (0xC8); with `+0xFC = 0x7FFFFFFF` no tile counts as cached (`wcoord_was_cached` 0x008B13B0 compares `CoordInfo + 0x6C + lod*4` with `+0xFC`), so the next rebuild re-adds them all.
- `ground_guard`, every frame before TerrainOut::render: counts the blocks in view per stream; above 30 % of 2621 in the fullest one it caps the zoom-out distance at `dist * sqrt(0.8 / ratio)` (lowered at once, raised only below 65 %), and when a block past 2621 is in view while the count is back under 80 % it calls `set_zoom(5)` and sets the camera's outdate (logged as "ground: a stream used block ...", at most once a second).
- `TerrainVis::set_zoom(int)` is 0x008B3190 (thiscall, `ret 4`); `TerrainOut *` is `*0x00C06218` (MiscAccess::terrain), TerrainVis at +0x533C, 0xC streams.
- Ground broke again on 2026-11-05 (savanna map, Information Age start, 2559x1599, extra zoom out): large black areas with trees drawn on them, ground in straight slanted bands, and a band of tall vertical streaks. The log had no "ground:" line, so `ground_guard` never cleared the ground.
- Why its clear branch cannot catch the texture streams: `set_pending_wcoords(arg)` (0x008B26F0) calls `build_index_buffer(s, arg)` (0x008B0300) for each stream. Only streams n-6..n-2 build indices (`block * 25 - first`, unsigned short, only blocks with the current stamp). The texture streams (s < n-6) and the last one go to `squeeze_cache(s, s == n-1, arg)` (0x008B0190). It moves the highest block in view into every hole below it (`move_stream_bucket` 0x008B0080 copies `vpt` vertices from `top * vpt` to `hole * vpt`; vpt = 25/25/9 by LOD, 9 with detail >= 3). Then it sets the draw count `[+0x60][s] = (top + 1) * vpt`, where `[+0x20][s]` (word) is the top block. So in those streams the blocks in view are always 0..top, and "top past 2621 while in view <= 80 %" can only happen in streams n-6..n-2.
- Stamps: `add_visible_wcoord` (0x008B2EB0) refreshes a tile that is already cached (`CoordInfo+0x6C+lod*4 == +0xFC`) to `game+0x848` (CoordInfo and block stamp). New tiles get it in `set_pending_wcoords`, whose end with arg 0 sets `+0xFC = game+0x848`. So counting stamps == `+0xFC` before TerrainOut::render gives the previous rebuild's view, as intended.
- Measured live on 2026-11-05 (2559x1599, savanna map, read with ReadProcessMemory, 2 samples a second): the visible tile list `[0x00C11CF8]` holds 117-290 tiles at level 6, 225-346 at level 5, about 345 at rest at level 4, and 690-708 at level 3. The last stream (n-1) holds every visible tile (top word + 1 = the list count). Its draw count `[+0x60][n-1]` is tiles x 25 at LOD 0/1 and tiles x 9 at LOD 2, at most 8650 vertices (level 5) and 6372 (level 3). The other streams draw at most 2688. Block arrays: 200 per stream, 780-800 for the last one. So none of the ground's limits is close at level 3: 2621 blocks, 16383 vertices for a Pre-Transform batch, 65536 indices.
- Second picture the same day (another map, French, level 3): the whole ground drawn as a dark grid one tile wide (about 76 px at level 3) with speckled texture between the lines; a hill and the trees normal.
- The fog is not it either: `fill_fog_texcoords` (0x008B19F0) always fills the 5x5 `FT_CUR`/`FT_DEST` whatever the LOD, as fog.c does.
- Clip planes: `Camera::update_transforms` 0x008430A0 puts the eye at -dist (times `camera_scale` 0x00C0625C for the main camera) and calls `compute_clip_planes` 0x00842950. Near (`cam+0x130`) = eye height - 3840; far (`cam+0x134`) = the distance from the eye to the plane z = -10 along a ray (+0x12C = 45, half of it again halved). Read at level 6: eye (`cam+0x74..`) z 6182 = dist / 2, near 2342, far 21507 (1.74 x dist). The near margin in front of the screen centre is dist / 2 + 3840: 0.81 x dist at level 6, 0.655 at level 4, 0.60 at level 3. Not yet tied to the picture.

## Sprite trim and the sub-pixel fix (subpixel.c, 2026-10-28)

- `Sprite::init_32` 0x0054C1D0 cuts fully transparent rows off the top (count at `Sprite+0x4C`) and the narrowest run of fully transparent columns off the left (`+0x48`); the test is alpha byte == 0. `+0x3C` is the height left.
- `Sprite::draw` 0x0053E260 reads the scale from `GraphSys` vtable +0xF8 (num x, num y, den; `SpriteMethod::execute` sets them through +0xF4 as `(int)closest, (int)closest, (int)dist`) and adds `trim_x * num / den`, `trim_y * num / den` to x, y with `idiv`: a truncated whole-pixel term.
- The game's building art has trim 0 (cut to the edge; `tower_6` has 2). The nations' new art keeps the original canvas around rescaled art: trims of 20-90 px (`village_0a` Mongol 60, 56; NE `library_0m` 47, 82). So only our buildings kept stepping a pixel while zooming after the sub-pixel fix. `subpixel_begin` now adds `trim * num / den` exact minus truncated, read from the Sprite in the packet; nation_art.c calls it after its swap, right before the game's draw_build.
- `SpritePacket::set_sprite` 0x009171C0 sets the hotspot from the untrimmed size: offset x = width / 2, y = height - width / 4 (both ints).
- Bigger art than the original canvas (2026-11-01, Russian church +35 %): nation_art.c swaps only the Sprite pointer, so the packet keeps the original's hotspot, and the art is placed from the original canvas's top-left plus the replacement's trim. A canvas grown to the right and down therefore lands right as it is; one grown left / up is moved back by lowering the loaded sprite's trims (`+0x48`, `+0x4C`) by the growth, given in nation_art.ini as `<file>, dx, dy`. Not yet seen in game: whether selection, the health bar or the "behind" outline use the sprite's size is unknown.

## Arrow-key scroll delay (ron_camera.c `instant_keys`, 2026-11-08)

- `Camera::check_scroll` 0x008440F0 runs every drawn frame (from `Game::loop_render`, 0x00591C0D) but reads the keys from the array `Game+0xAF0` (BYTE[256], tested `>= 0x80`): arrows at `+0xB15..+0xB18` (VK 0x25..0x28), numpad 2/4/6/8 at `+0xB52/+0xB54/+0xB56/+0xB58`, and no scroll at all while Ctrl `+0xB01` or Alt `+0xB02` is down. So a press, and a release, reaches the camera up to one tick late, and a held key between ticks is invisible. Paused, the array never changes.

## Picture look (postfx.c, 2026-10-29)

- d3dgl (`sbl\d3dgl.map` has its symbols) compiles every shader at run time with `D3DCompileFromFile` / `D3DCompile` (imports of d3dcompiler_47) from `shaders\*.hlsl`, the post ones as entry `PS`, `ps_4_0`. The file is opened through CreateFileW, so `override_redirect` can serve another one; the compiler resolves `#include` from the name it was given (`shaders\...`), so the game's headers are still used. A `D3DCompile` test with the game's path as the source name finds them the same way, from any working directory.
- `Scene::render` after the scene and Nuke::draw: graphsys vtable +0x228, then +0xBC `get_tonemapper` -> `D3D11ToneMapper::do_run(bool bloom)` (vtable 0x100E4FC4 +4 = 0x10044A30; the bool is `[graphsys+0x104]+0x58 == 2`), then +0xC0 `get_anti_alias` -> `D3D11AntiAlias::run` 0x100186D0 (vtable 0x100E44AC +0). Only then `draw_drag_box`, `ObjectsOut::draw_overlays` (health bars), shockwaves and later the interface. So both passes see the scene alone.
- `do_run`: `do_luminance`, `do_tonemap` (`ps_tonemap.hlsl`, two targets: Color and Bright), and with bloom `do_blur` + `do_blend` (`ps_blend_screen.hlsl`, screen blend, writes alpha = luminance); without bloom the toned buffer is copied to the screen target (CopyResource) as it is, alpha 1.
- `D3D11AntiAlias::run` copies the screen target (`d3d_sys+0xCF4`) into a temp texture and draws it back through `ps_fxaa.hlsl` (FXAA 3.11, `FXAA_PC`, luma from **alpha**). On only when the pref `Anti-Aliasing` (rise2.ini, `[RISE OF NATIONS]`, default 1) is set (`+0x24`, read in `init` 0x10017B80). Since only the bloom blend writes luminance into alpha, with bloom off FXAA read a constant luma and smoothed nothing; postfx writes the luminance in the tone mapper.
- Anisotropic filtering is already on: `D3D11GLGraphicCard::set_sampler_states` 0x1002BB60 makes every sampler that is not point-filtered (`RenderState+0x50 & 0x400000`) `D3D11_FILTER_ANISOTROPIC` with MaxAnisotropy 16, address W clamp, LOD range unlimited. The building and unit sprites are point-filtered on purpose (pre-rendered for the zoom levels).
- Free slots: pixel shader constant buffer b7 (b0-b6 are d3dgl's). An unbound constant buffer reads 0, so postfx's switch (b7, x = the game's look, y = comparison) means "look on" when it is not bound. It is bound in our `do_run` (vtable slot patched), before the tone mapper and FXAA draw.
- UVs of the screen quad (`vs_screen_quad.hlsl`) run 0..1 left to right, so `uv.x < 0.5` is the left half in both passes.

## Water (postfx.c, 2026-10-29)

- Seas and lakes: `TerrainOut::render_water` 0x00852CD0 sets the technique "Normal Water" when `[graphsys+0x104]+0x5C == 2` (the water quality), else "Min Water" (`RenderControl::get_technique`, the TerrainOut's control at `+0x665C`, current one at `+0x6678`). Both are made in `TerrainOut::one_time_init` (0x0085C47A, 0x0085C732): flags `|= 0x204`, and when the card can (`card vtable +0xA0`) `|= 0x384000` (Normal) or `0x184000` (Min). Rivers have their own `RiverSectionOut::render_water` 0x0088CE80 (not looked at; probably the same techniques).
- RenderState `+0x50` flags to uber shader defines (`D3D11GLGraphicCard::set_shader_options` 0x1002DB30; the define names are the table at 0x100DD0A0, index = option): 0x200 (and `d3d_sys+0x830`) ENABLE_LIGHTING (1); 0x4000 (and `card+0x30C & 0x2000000`) USE_NORMAL_MAP (18), and inside it 0x80000 ANIMATE_WATER_NORMALS (23); 0x100000 SPEC_MODEL_TORRANCE (24); 0x200000 HAS_SCREEN_REFLECTIONS (25); 0x400000 is the point filter. So Normal Water = lit, normal-mapped, animated, Torrance specular, screen reflections; Min Water the same without reflections. Only the water has ANIMATE_WATER_NORMALS, so code inside that `#ifdef` touches nothing else.
- The uber shader is compiled per permutation by `D3D11PixelShader::compile` 0x1003FC50: `D3DCompile(text, len, "shaders\ps_global.hlsl", macros, D3D_COMPILE_STANDARD_FILE_INCLUDE, "PS", "ps_4_0", OPTIMIZATION_LEVEL3)`, the text read once from the file (so `override_redirect` serves ours).
- Reflections: with flag 0x200000 `set_render_state` binds t5, t6 from `card+0x3B4` (a `ReflectionManager`), whose textures `D3D11GLGraphicCard::frame_ended` 0x1001D280 fills at the end of every frame by copying `d3d_sys+0x1238` (the HDR scene, the tone mapper's input) and `d3d_sys+0xD04` (the depth buffer). So the water reflects the previous frame, in HDR. The game's march: 10 steps of 10 world units (a tile is about 192), a hit only within 0.00075 of the hardware depth, so almost nothing was ever reflected.
- postfx's march: 24 steps from 20 units growing by 1.1 (about 1800 units), the hit when the ray is 2 to 200 units behind the stored depth (linear depth `w = P34 * P43 / (z * P34 - P33)` from `gProjection`, so it does not matter which way the depth runs), 5 halvings between the last two points, faded at the screen edges and towards the end of the ray, mixed over the water by `water_reflections`; plus a sharp glint `pow(N.H, 300)` and a sky tint by `(1 - N.V)^3`, and the wave normals' slope times `water_waves`.

### Chasing a moving cast target (cast_follow, found 2026-10-30)

The user: a Senator told to bribe a walking unit "runs after it, stops now and then and looks, runs again, turns back or walks in circles until it dies".
- `Unit::do_cast(UnitOrder *)` 0x005EBFE0, every tick of the cast order: the order's data (order virtual `+0x7C`) has `+8` target id, `+0xC` target player, `+0x20` craft. ## Units making way (shove.c)

Found 2026-10-27 (the user: units cannot get past idle ones).
- `Unit::move_step(MoveOrder *, int)` 0x005FAF30 checks the next step with `Unit::detect_unit_collision(Coord x, Coord y, int, int, int, int, int)` 0x00617060 (`ret 0x1C`). It walks the 9 cells around the step (`move_x` 0x00ADCAF0 / `move_y` 0x00ADC400, `WorldData::get_down` for the object there); on a collision it stores the blocker in the mover, **word `+0x8A` = its id, byte `+0xB3` = its player**, word `+0x8C` = 0, and returns 1; when the way is free it stores -1 / 0xFF and clears the blocked counter word `+0x88` if the last block (`+0x48`, a frame) is more than 5 frames old. Units of the same move group (short `+0x80`) moving the same way, and some order types, do not count as blockers.
- On a collision `move_step` calls `Unit::resolve_unit_collision(Coord, Coord)` 0x005F9D30 (thiscall, `ret 8`, prologue `push ebp / mov ebp,esp / push -1`; its only caller, 0x005FB7C1). It reads `+0x8A` / `+0xB3`; an enemy blocker is attacked (`add_attack_order`); otherwise it counts the block (`+0x88`++, `+0x48` = frame) and looks at the blocker's action type (`UnitData::action_type` 0x0060A850): a move-type order (`is_move` 0x0046F050: 1 Move, 2 AttackTo, 3 ExploreTo, 4 FleeTo, 0x12 Form, 0x13 GroupMove, 0x15 GroupAttackTo; or 0xE Cast of craft 0x28A) makes the mover wait (`[mover + 0x68] |= 0x40`) while both blocked counters are under 32 (128 when the player's `GameDaemon` repath count is 4 or more). Anything else, an idle unit included, is walked around: the path stack `+0xB8` is popped, `CollCheck::collide_here` 0x00682540 tests a sidestep, `Unit::set_new_location` and `PathFinder::find_upath` 0x00688EB0 make a local path (at most 16 per player per frame, `GameDaemon[player]`). When two units block each other the mover gets a random wait (`game_random` 0..8 + 1 into order `+0x18`). **The game never moves the blocker.**
- OrderIndex values (each order class's `get_type`): 0 Patrol, 1 Move, 2 AttackTo, 3 ExploreTo, 4 FleeTo, 6 Build, 7 Gather, 8 Board, 9 AwaitBoard, 0xA Attack, 0xB Follow, 0xC Guard, 0xD Repair, 0xE Cast, 0xF Trade, 0x10 Strafe, 0x11 AirPatrol, 0x12 Form, 0x13 GroupMove, 0x14 GroupAttack, 0x15 GroupAttackTo, 0x16 GroupPatrol, 0x17 AttackGround, 0x18 AirAttackGround, 0x19 SpecialAnim, 0x1A Garrison, 0x1B Think. - Orders the game gives by itself: `Unit::add_move_order(Coord x, Coord y, int, int, QueuePos, int, int, Coord, Coord)` 0x00616ED0 (`ret 0x24`; the 7th argument is not read; it calls `add_move_facing_order` with `find_angle`). `Animal::do_idle` 0x005D7460 wanders with `UnitType::find_nearby_spot(x, y, *ox, *oy, min 0xC0, max -1, step 0, start angle 0x55555555, FilterIndex 3, id, player, 0, 0, -1, 0, -1)` 0x0061DE70 (`ret 0x40`, returns 0 when it found a spot: rings from min to max distance, 16 directions from the start angle) and then `add_move_order(x, y, 1, 0, QueuePos 2, 0, -, -1, -1)`. `find_angle` 0x0092D130 takes dx in ecx, dy in edx and returns a binary angle (2^32 = a full turn).
- shove.c hooks `resolve_unit_collision`'s entry. Before the game's code: if the blocker is a land unit of the mover's own player (not of its squad or move group) and every soldier of its squad has no orders, is not a decoy (`+0x68` bit 0), not dug in (`+0x68` 0x2000000, `+0x6C` 0x1000 / 0x20000) and not held in a Nest (entrench.c), it looks for a free spot 0x100-0x240 world units away, starting square to the mover's approach (the side by the captain's id), and gives every soldier of the squad `add_move_order` by the same step. The game's code then sees a moving blocker and waits for it. A squad moved aside is not moved again for `[make_way] cooldown_frames` (45). Simulation-side and deterministic (frame clock, no random); the cooldown table is not saved.

## Map size (looked at 2026-11-05, nothing patched)

Asked by the user: can a map be larger than the largest one in the game? Static research only.

- **Where the sizes live:** `Data/rules.xml`, `<CATEGORIES id="mapsizes">`, one `<DATA>` per size: Tiny 40, Arena 50, Small (key Medium) 60, Standard 70, Large 80, Huge 90, **Big Huge 100** (key "Big Huge"). `Game::init_rules_data` 0x0058F316 loads them with `Categories::init(7, xml, "mapsizes")` 0x006F21D0 into `map_sizes` 0x00E7FC98 (array pointer `[0x00E7FCA8]`, 0x58 bytes per entry, the DATA value at `+0x3C`). The 7 only preallocates the array. `GameInfo::get_map_size_name(MapSizeIndex)` 0x005D46F0 has 7 names (index 0-6).
- **Setup menu:** `SetupWin::setup_combos` 0x005C0133 adds all 7 entries (`IFaceComboBox::category(7, map_sizes, game+0x26, 1)` 0x007FF0B0 loops over every entry, no filter), so Big Huge is offered. `setupwin_map_size_is_bad` 0x00CAB39C (set in `SetupWin::update_interface` 0x005B6256) only paints the combo red / green when the size does not suit the player count.
- **From index to world:** `Game::init` 0x0058CDB4: `W = map_sizes[game+0x26].+0x3C`; map style index 0x10 (New World, `game+0x25`) gives `W * 11 / 10` rounded to even, **capped at 100**; flag `setup+0x821 & 2` halves it (rounded to even). Then `World::init(W, W)` 0x0058CFFC: maps are always square.
- **World layout** (`World::init(unsigned short, unsigned short)` 0x006B76F0, `world` 0x00C097E8, `GameAccess::world` `*0x00C06188`): `+0 / +4` W, H in WCoord blocks; `+8` W*H; `+0x18 / +0x1C` 4W, 4H (TCoord, 4 per WCoord; script `get_map_size()` 0x009E4CB0 returns `+0 * 4`, `world_x_size` / `world_y_size` read `+0x18 / +0x1C`); `+0x20` 16WH; `+0xC / +0x10` 2W, 2H (FCoord, fog); `+0x24 / +0x28` W/2, H/2. Arrays, all malloc'ed from these: `+0x134` WData[W*H] (0x1C bytes each), `+0x138` 2 bytes per TCoord, `+0x15C/+0x160/+0x164` 1 byte per FCoord, `+0x168` 1 byte per WCoord, `+0x13C` 8 arrays of 4 bytes per (W/2 * H/2), plus `DynamicBitMask` `+0xF0` of W*H. At W = 100 that is about 1 MB.
- **The largest entry is the engine's maximum:** right after loading, `init_coord_lookup_array(map_sizes[6].+0x3C * 4)` 0x0058F34A sizes the coordinate divide tables (`orig_div_3_table` 0x00CAB3AC, `div_3_table` 0x00CAE5FC) from the LAST entry. So raising Big Huge's DATA raises the limit with it; a value above the last entry would overrun those tables.
- **Coordinates are 32-bit:** `World::get_wdata` 0x0046D220 reads WCoord x / y as dwords; only `World::init` takes unsigned short (up to 65535). No 8-bit packing found.
- **No fixed map-sized statics:** no static array in .data/.bss between 0x00C00000 and 0x00F00000 is larger than 16 KB except `terrain` 0x00C0B0F0 (27 KB, the object), `combat_table`, `IncrementalLoad::buffer` (1.5 MB load buffer), `leaders`, `command_manager` and UI objects. `Terrain::init(int,int,int)` 0x00850F70 and `WorldMapFog::init` allocate by world size; `PathFinder::init` 0x00689EC0 uses recycled tree pools, no grid.
- **Fixed numbers found that do touch maps:** `Map::make_rivers` 0x006934E2 caps a river value at 399; the mapstyle values scale against Standard (`World::scale_by_axis` 0x006B76B0 / `scale_by_area` 0x006B2B10: `value * W / map_sizes[3].+0x3C`, at least 1), so larger maps get more and bigger features by themselves. PathFinder has fixed search budgets set in `PathFinder::init` (0x37, 0x64, 0x64, 0x21C, 0xF0, 0xC8, 0x3C, 0x258 at 0x00E85EE0..0x00E85EFC); long paths on a much larger map may hit them.
- **Untried risks:** the renderer's terrain buffers and the fog texture at sizes the game never made; AI planning cost; frame rate with 8 players. Memory: `riseofnations.exe` is large-address-aware since `package/install.ps1` sets the flag (characteristics 0x122, 4 GB; the original is kept as `riseofnations.exe.no-laa.bak`).
- **Cheapest way to try:** change Big Huge's `<DATA>` (it already is the last entry, so the lookup tables follow) in our `rules.xml` override (`romania/mod_override/Data/rules.xml` is the copy that wins), e.g. 130, and start a Big Huge game. Rename it in the menu through `name=`. All players in multiplayer need the same rules.xml.

Seen in an Information Age game started with "All Technologies": a new tower was laid as the plain Tower (750 hits + bonus, medieval icon), not the Bunker. The rules of the four levels are the game's own (only Romania's TRIBE_MASK differs).

- `LeaderData::type_avail` 0x006E33A0, building branch (0x006E35AF): a building with `[bt+0x3C] >= 0` and flag 4 at `[bt+0x2C0]` is "2, not available" until its bit at leader `+0x6C18` is set (the same bitset `LeaderData::has_upgrade` 0x00471380 reads). The bits are set as techs are gained (`Leader::gain_tech` 0x006DCB60 calls current_upgrade).
- Callers of current_upgrade do not include `Group::action_build`, `Objects::init_build`, `Leader::produce_building` or `Leader::create_buildings`: the type laid is the one the button or the planner gives.
- Type indices: Tower 0x1B7, Keep 0x1B8, Stockade 0x1B9, Bunker 0x1BA, Fort 0x1BB .. Redoubt 0x1BE. `[type+0x48]` is the next level, `[type+0x44]` the level below.

So a level is "gained" like a tech, once; a building laid later at a lower level is never upgraded.
- **Obsolete lower levels:** `LeaderData::type_eligible(type, 1)` 0x006DBD10 (from 0x006DBFAC) walks `[type+0x48]` (through `get_graft`): when a higher level has `has_preq` and its `+0x6C18` bit, the type is not eligible (so not 4). Flag 0x200 at `[+0x2B4]` of a level and 0x80 of the type add a case. With a second argument of 0 the walk is skipped.
- **The computer's buildings:** `Leader::create_buildings` 0x006C1BE0 offers every building type with `type_avail(type, 1) == 4` (0x006C1E09) and has no current_upgrade call; the type it hands to `produce_building` is laid as is (`Group::action_build`'s vtable `+0x84` call at 0x007078DB is the type's can-pay, not a conversion).

## Late-game slowdown (looked at 2026-11-05, nothing patched)

- A 1h+ match, 8 players, Information Age, ~30 nukes: the game crawled. Measured live with a thread sampler (suspend the main thread, read EIP and scan its stack for return addresses into the exe; symbols from `tools/rdis_syms.txt`, exe VA = 0x400000 + module offset).
- Memory was not it: the minute line said 1.6 of 4 GB, largest free block 2 GB.
- The main thread used one full core. Inclusive: `Game::loop_render` ~71 %, `Scene::render` ~45 %, `BaseScene::render_end` ~40 % (waiting on the GPU), `CommandManager::process_turn` ~19 %. Our DLL hardly shows up at all.
- The game ran on the **Intel integrated GPU** (`igd10umt32xe.dll` loaded, 3D engine 98 % busy) at 2560x1600, while the laptop also has an RTX 5080. Windows picks the power-saving GPU when `HKCU\Software\Microsoft\DirectX\UserGpuPreferences` has no value named after `riseofnations.exe`'s full path; `GpuPreference=2;` there = high performance (read at process start). `d3dgl.dll` in the game folder is the game's own D3D7-to-D3D11 layer, so DXGI's per-app preference applies.
- The simulation half: `CheckSums::check_all` 0x00936560, called by `process_turn` (0x0093F103, 0x0093FB63) **every turn**, walks the whole game state through `CheckSum::walk_function` / `adler32` (units, deaths, pathfinder stacks and `Types::walk_rules_data` / `Balance::walk_rules_data`, the whole rules data each time). `adler32` alone was ~12 % of the main thread, all of check_all ~18 %, growing with the number of objects. It is vanilla (the multiplayer out-of-sync check); each part's flag comes from 0x00463930 (`ecx = [0x00CC4B3C]`). Skipping it in single player would save that time but is not done.
- `nukefx.c` soften_flash logged one line per blast by remembering only the last start: with two blasts lit at once it logged both every frame (900 lines in a match). Fixed: it remembers the last 8.
